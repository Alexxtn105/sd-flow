# SysDesign Flow

*[English version →](README.md)*

Визуальный тренажёр по проектированию высоконагруженных систем: собери схему из блоков
(клиенты, балансировщики, гейтвеи, сервисы, БД, кэши, брокеры, S3, CDN) — и узнай, какой RPS она
держит, где узкое место, какая latency p99, сколько петабайт накопится за год и сколько это стоит.

**[Открыть редактор →](https://alexxtn105.github.io/sd-flow/)**

## Статус: фаза 3 завершена (v1.0)

Позади редактор схем (фаза 0), стационарная модель нагрузки (фаза 1) и режим «Задания» (фаза 2).
Фаза 3 добавила ход времени, измерители, вторую волну каталога и десять новых заданий.

* **Каталог — 109 блоков в 14 группах**: волна MVP (44) плюс волна V1 (65). Модель ёмкости
  заполнена у 83 блоков — у всех, кто несёт трафик; у клиентов её нет по построению (они
  источники), у контейнеров, линков и проб её не бывает. 98 родовых иконок, вендорских логотипов
  нет принципиально.
* **21 задание** уровней 1–5 с приёмкой по предикатам, Realism Gate, антипаттерн-линтером,
  рубрикой по семи осям и звёздами.
* **16 сценариев**, из них 10 с ходом времени.
* Расчёт детерминирован: seed выводится из схемы, сценария и версии модели, `Math.random()`
  в движке запрещён.

### Что считает движок

* **Стационарный решатель потоков** — демпфированные итерации (ω = 0.5, до 50 проходов, порог
  сходимости 0.001) с усилением ретраями, поглощением трафика кэшем и автоскейлингом.
* **Ёмкость с названным ограничителем** — `cpu`, `iops`, `connections`, `ops`, `memory`,
  `partitions` и ещё полсотни имён ресурсов. Каждый ограничитель показывает формулу с
  подставленными значениями, а `boundBy` выводится прямо на блок.
* **Очереди** — аппроксимация Сакасэгавы для G/G/c с поправкой на вариативность потока и
  обслуживания: ожидание, глубина очереди, сброс нагрузки сверх ёмкости, таймауты.
* **Latency p50/p95/p99** — Monte-Carlo по дереву вызовов, 20 000 сэмплов на поток: логнормальное
  время обслуживания, ожидание в очереди, `sequential` против `parallel`, ретраи с
  экспоненциальным backoff, таймауты и промахи кэша.
* **Transient-режим** — прогон по шагам времени вместо одного среза: лаг автоскейлера, очереди
  с памятью между шагами, прогрев кэша. Ряды нагрузки, утилизации, p99, backlog, ошибок и числа
  инстансов рисуются таймлайном в дашборде, полосой отмечено время нарушения SLO.
* **Hit ratio кэша выводится, а не задаётся** — из распределения Ципфа по ключам, объёма памяти,
  TTL и доли записи. Кэш размером с базу не спасает, если TTL короче интервала повторного
  обращения, и это видно на цифрах.
* **Хранилище, логи, egress, стоимость** — накопление на горизонте 365 суток, объём логов из
  `logLinesPerRequest × logBytesPerLine`, четыре профиля цен (AWS, GCP, Hetzner, on-prem).
* **Доступность** — с учётом резервирования и 5% коррелированных отказов (иначе три реплики по
  99.9% давали бы девять девяток), поиск единых точек отказа.
* **Мультирегион** — доли трафика по регионам, трафик и стоимость репликации,
  `RPO = p99 лага репликации`, `RTO = обнаружение 30 с + TTL DNS 60 с + failover блока + прогрев
  60 с` (плюс 900 с при ручном переключении), сравнение с целевыми значениями.
* **Периметр сети** — группы `vpc` и `k8s-cluster`: межсетевой хоп и выход через NAT ложатся
  в задержку, control plane — в стоимость, перегруз NAT и превышение потолка подов приходят
  находками.
* **Симуляция аномалий согласованности** — шесть типов: устаревшее чтение, «не вижу свою запись»,
  потерянное обновление, конфликт записи в мульти-мастере, потеря записи при last-write-wins,
  повторная обработка при at-least-once.
* **16 сценариев** — стационарные `baseline`, `peak`, `az-failure`, `region-failure`, `stale-read`,
  `write-conflict` и transient `spike`, `growth`, `black-friday`, `db-failover`, `cache-flush`,
  `thundering-herd`, `hot-key`, `slow-dependency`, `retry-storm`, `poison-message`.
* **Findings** — 15 правил движка (перегрузка, насыщение, шторм ретраев, SPOF, горячий ключ,
  растущий backlog, чтение без кэша, ретраи без идемпотентности, egress съедает счёт и другие),
  структурные проверки компилятора и аномалии согласованности — каждая с объяснением и
  подставленными числами.

### Измерители и водопад

Одиннадцать блоков `probe-*` цепляются к любому узлу схемы и снимают показание: RPS, latency,
утилизация, лаг очереди, проекция хранилища, стоимость поддерева, SLO и error budget, девятки
доступности, разбивка трафика, тепловая карта, водопад задержки.

Показание выводится прямо на блоке пробы и красится по статусу; двойной клик открывает
перетаскиваемое окно с числом, формулой и её входами. Если проба ни к чему не прикреплена или
блок не даёт нужной величины — окно объясняет причину, а не показывает ноль.

Четыре измерителя не считают, а рисуют. `probe-latency` раскрывает **гистограмму** с отметками
p50/p95/p99 — она собирается из посэмпловых массивов Monte-Carlo, которые движок и так держал в
памяти, и показывает хвост, который одно число прячет. `probe-rps` и `probe-utilization` дают
**ряд по времени**, а в стационарном сценарии честно говорят, что истории нет.
`probe-heatmap` **проецируется на схему**: канвас берёт цвет узла у пробы, но полоса утилизации у
каждого узла остаётся своей.

**Водопад задержки** раскладывает поток по хопам: ширина полосы — собственный вклад хопа,
положение — накопленное время, отдельной строкой показано, сколько квантиля хопы не объяснили.
Живёт в дашборде (с выбором потока и квантиля p50/p95/p99) и компактной версией — в окне
пробы `probe-waterfall`.

### Режим «Задания»

21 задание уровней 1–5: от статического сайта и сократителя ссылок до платежей, матчинг-движка,
глобальной ленты и прямых трансляций. У каждого — брифинг с исходными данными и SLO,
машиночитаемые требования, батарея сценариев, подсказки с ценой в баллах и эталонные решения,
которые открываются после сдачи.

Приёмка идёт конвейером: компиляция → Realism Gate (ловит «схемы-обманки») → предикаты →
батарея сценариев → линтер → рубрика по семи осям → звёзды. Вердикт детерминирован и всегда
показывает конкретное нарушенное требование.

### Чего ещё нет

* **`splitByFlow` у `probe-rps`**: таймлайн складывает все потоки в одну интенсивность, разложения
  по потокам во времени нет. Параметр есть, эффекта у него нет.
* **Гарантию порядка можно объявить только двум брокерам** — `orderingScope` у Kafka и `queueType`
  у SQS. RabbitMQ, NATS, Kinesis, Redis Streams и SNS считаются неупорядоченными без права
  возразить, поэтому аномалия A7 может их переоценивать.
* **Сценария `split-brain`** — для него нужна модель расхождения и слияния реплик, а не только
  форма входного потока.
* **Зеркальных регионов `mirrorOf`** — каждый регион описывается своими узлами вручную.
* **Потолок подов `k8s-cluster`** диагностируется находкой, но расчёту не навязывается.
* **Волны V2 каталога** — 20 блоков из [docs/01-components.md](docs/01-components.md) §15.
* `custom`-предиката и диффа с эталонным решением, режимов «Инцидент», «Гольф» и «Интервью»,
  конструктора заданий и лидербордов — это фаза 4.
* Пересчитывается всегда вся схема целиком — инкрементального пересчёта по подграфу нет.

## Демо-схемы

Обе открываются из выпадающего списка в шапке и служат приёмочным тестом
(`tests/engine/demo-schemes.test.ts`).

**«Видеоплатформа»** — 1 млрд DAU, CDN поверх S3, отдельная ветка API: балансировщик, сервис,
Redis, Postgres, Kafka и 2000 воркеров-транскодеров. Тест закрепляет: 80–130 ПБ/сут исходящего
трафика и 8–30 Тбит/с полосы; до origin доходит меньше 15% запросов, остальное снимает CDN;
у каждого нагруженного узла есть названный ограничитель; полный расчёт на 20 000 сэмплов
укладывается в 100 мс.

**«Платежи в двух регионах»** — 5 млн DAU, глобальный балансировщик, два региона (`eu-west-1` и
`us-east-1`), в каждом сервис и Postgres, политика мультирегиона `active-active` с двусторонней
репликацией и разрешением конфликтов `lww`. Тест закрепляет: частота конфликтов записи ненулевая,
потери записи при LWW равны половине конфликтов, переключение на `single-writer-per-key` обнуляет
и то и другое; трафик раскладывается по двум регионам, RPO и RTO считаются; сценарий
`region-failure` гасит узлы одного региона, второй продолжает обслуживать.

## Запуск

```bash
npm install
npm run dev        # http://localhost:5173/sd-flow/
```

| Команда | Что делает |
|---|---|
| `npm run dev` | Дев-сервер с горячей перезагрузкой |
| `npm run build` | Проверка типов и продакшн-сборка в `dist/` |
| `npm run preview` | Локальный просмотр собранного бандла |
| `npm run lint` | ESLint 9 (flat config) |
| `npm run typecheck` | `tsc --noEmit` |
| `npm test` | Vitest: 331 тест в 22 файлах — реестр, каталог, порты, стор, сериализация, движок, сверка модели с теорией очередей, transient, пробы, задания, локали, демо-схемы |

Деплой — GitHub Actions по пушу в `main`: lint → typecheck → тесты → сборка → GitHub Pages.
Приложение ставится как PWA и работает офлайн; схему можно отдать ссылкой, канвас — выгрузить
в PNG, результат расчёта — в Markdown.
