# 03. Соединения: семантика и визуализация трафика

Приложение к [PRD.md](../PRD.md). Отвечает на вопрос из ТЗ: *«соединительные линии могут быть
чтение, запись, а может то и другое — нужно исследовать, что лучше»*.

---

## 1. Почему рёбра здесь важнее, чем в dsp-flow

В `dsp-flow` ребро — это просто «сигнал течёт отсюда сюда», а вся семантика в блоках. В system
design **ребро несёт половину смысла архитектуры**: одно и то же «Сервис → Postgres» может быть
1000 точечных чтений в секунду по 200 байт, а может быть 50 батчевых записей по 2 МБ с
синхронной репликацией. Это разные системы с разными узкими местами.

Поэтому ребро в SysDesign Flow — это **профиль вызова**, а не стрелка.

## 2. Что обязано нести ребро

| Поле | Зачем нужно в модели |
|---|---|
| `kind` | sync / async / replication / stream / cdc / batch — определяет, входит ли в цепочку latency |
| `protocol` | http / grpc / sql / redis / kafka / amqp / s3 / ws / internal — валидация совместимости портов |
| `calls[]` | Профили вызовов (см. §3): операция, доля, fanout, payload |
| `fanout` | Сколько вызовов downstream на один входящий запрос — умножает λ |
| `payload.requestBytes` / `.responseBytes` | Сеть, egress-стоимость, ограничение по пропускной способности |
| `policy.timeoutMs` | Отсечка хвоста latency, источник ошибок |
| `policy.retries` + `retryBudget` | Усиление нагрузки, retry storm |
| `policy.circuitBreaker` | Обрыв каскада |
| `policy.idempotent` | Проверяется предикатами заданий (ретраи без идемпотентности = антипаттерн) |
| `consistency` | strong / bounded-staleness / eventual — для рёбер к репликам |
| `readRouting` | primary / replica / nearest / sticky-after-write — доля чтений, способных увидеть устаревшие данные |
| `readYourWrites` | none / sticky-primary / version-token / wait-for-lag — планировалось как поле ребра; в коде роль закрыта параметрами хранилища `consistencyModel`, `stickyReadShare` и `staleReadPolicy` |
| `deliverySemantics` | at-most-once / at-least-once / effectively-once — для async-рёбер |
| `orderingGuarantee` | none / per-key / per-partition / global |
| `staleToleranceMs` | Сколько устаревания допустимо для этого вызова (порог, ниже которого аномалия не считается ошибкой) |
| `weight` | Доля при ветвлении (балансировка) |
| `pull` | Для брокер → консьюмер: данные идут по стрелке, но инициатор — приёмник |
| `label` | Подпись связи от игрока: «отдаём чанк», «инвалидация кэша». На модель не влияет, поле необязательное; пустая подпись в схему не пишется |

**Тип нагрузки (`protocol`).** Значение выбирается из пересечения протоколов выходного порта
источника и входного порта приёмника — то есть из того же списка, которым проверяется
совместимость при рисовании связи. Первый общий протокол ставится по умолчанию при создании ребра,
остальные доступны в инспекторе селектом «Тип нагрузки»; на линии значение видно подписью рядом с
именем связи — моноширинной плашкой с человеческим названием (`HTTP`, `gRPC`, `Redis`), а не
идентификатором поля. Названия лежат в словаре `protocol.*` пространства имён `common`, и обращаться
к ним нужно с явным префиксом `common:`: из пространства `params`, на котором сидит подпись линии,
ключ не разрешается и на холст падает сам ключ. Показ плашки настраивается — §5.3.
При импорте чужой схемы поле дописывается, а несовместимое значение (`kafka` на
ребре к Postgres) заменяется на допустимое. На расчёт `protocol` не влияет: он описывает связь,
а нагрузку задают `calls[]` и `payload`.

## 3. Исследование: read/write — одна линия или две?

Рассмотрены четыре варианта.

### Вариант A. Одно ребро с атрибутом смеси `{read%, write%}`

```
Service ══════════════════════► Postgres        edge.ops = { read: 0.9, write: 0.1 }
```

| ➕ | ➖ |
|---|---|
| Схема остаётся читаемой: между двумя узлами всегда одна линия | Не выразить случай «чтение идёт в реплику, запись — в primary» без второго ребра |
| Мало объектов в графе → быстрый рендер и простая модель | Смесь скрыта в инспекторе, не видна на канвасе |
| Соответствует тому, как это рисуют на собеседовании | |

### Вариант B. Два отдельных ребра: read-ребро и write-ребро

```
Service ──── read ───► Postgres-replica
        ──── write ──► Postgres-primary
```

| ➕ | ➖ |
|---|---|
| Явно и честно: разные пути чтения/записи — норма (CQRS, read replicas) | При 30 узлах схема превращается в «спагетти»: рёбер вдвое больше |
| Каждое ребро можно параметризовать независимо (payload, timeout, консистентность) | Дублирование настроек, когда пути совпадают |
| Легко считать | Пользователь обязан заводить два ребра даже там, где это не нужно |

### Вариант C. Одна линия без разделения (только суммарный RPS)

| ➕ | ➖ |
|---|---|
| Максимально просто | **Ломает модель**: у БД read и write имеют разную стоимость (IOPS ×5), разную ёмкость и разные пути (реплики). Без разделения нельзя посчитать ни ёмкость, ни рост данных |

Отклонён.

### Вариант D (рекомендуемый). Одно ребро с массивом профилей вызова + действие «разделить»

Ребро несёт **список профилей вызова**, а не бинарную пару read/write:

```ts
interface CallProfile {
  id: string;
  op: 'read' | 'write' | 'delete' | 'scan' | 'publish' | 'consume' | 'transfer';
  label?: string;
  share: number;
  fanout: number;
  requestBytes: number;
  responseBytes: number;
  serviceTimeOverrideMs?: number;
  consistency?: 'strong' | 'bounded' | 'eventual';
}
```

По умолчанию у ребра два профиля — `read` и `write` — и в UI это две привычные ручки-ползунка.
Продвинутый пользователь может добавить третий («поиск по диапазону», «батч-вставка») и задать ему
своё время обслуживания и payload. Контекстное действие **«Разделить на read / write»** превращает
одно ребро в два независимых — ровно тогда, когда цели разные (реплика vs primary).

| Критерий | A | B | C | **D** |
|---|---|---|---|---|
| Точность модели | ○ | ● | ✕ | ● |
| Читаемость схемы | ● | ○ | ● | ● |
| Поддержка CQRS / реплик | ✕ | ● | ✕ | ● |
| Простота UI по умолчанию | ● | ○ | ● | ● |
| Расширяемость (батчи, сканы, publish/consume) | ○ | ○ | ✕ | ● |
| Сложность движка | ● | ● | ● | ○ |

**Вердикт: вариант D.** Одно ребро по умолчанию, с двумя визуальными жилами (read/write) и
возможностью разделить на два ребра или добавить произвольные профили. Это одновременно и просто
для новичка, и достаточно выразительно для 5-го уровня заданий.

### 3.1. Автовывод смеси

Смесь read/write **наследуется от Flow** и распространяется по графу: если во Flow «просмотр
видео» 98% чтений, то и рёбра на его пути несут 98/2. Пользователь правит только там, где
реальность отличается (например «сервис счётчиков просмотров пишет всегда»). Это убирает
80% ручной настройки.

Наследование работает так (формула — в `docs/02-simulation.md` §3.1): доли профилей на ребре
задают, **что** ребро делает и **какая часть** запросов по нему уходит, а пропорцию чтений и
записей приносит вызывающий. Практические следствия:

| Ребро | Что несёт при смеси вызывающего 90/10 |
|---|---|
| `read 0.9` + `write 0.1` (по умолчанию) | 90% чтений, 10% записей — то же, что и было |
| `read 0.5` + `write 0.5` | те же 90/10: доли внутри ребра задают только раскладку по профилям |
| только `read 1` (в реплику) | 90% запросов источника |
| только `write 1` (в primary) | 10% запросов источника |
| `read 0.27` + `write 0.03` (сумма 0.3) | 30% запросов, из них 90/10 |

Два ребра «реплика + primary» вместе несут ровно поток источника — раньше каждое из них забирало
поток целиком и трафик удваивался.

**Режим «Наследуется / Вручную» (`mixMode`).** Ребро с `mixMode = manual` берёт доли профилей
буквально, как они выставлены: это способ сказать «здесь смесь другая, и она не выводится из
вызывающего». Режим включается сам, как только игрок двигает ползунок доли в инспекторе, и
возвращается назад селектом «Смесь чтение/запись». В файле схемы поле пишется только для ручного
режима, поэтому старые схемы читаются как наследующие.

Наследовать нечего там, где во входящем потоке нет чтений и записей: у консьюмера, которому
приходят только `consume`, смеси нет, и его исходящие рёбра берут доли буквально независимо от
режима. Операции `publish`, `consume` и `transfer` в наследовании не участвуют вообще — событие
публикуется на каждый запрос, а не на его «записьную» часть.

## 4. Порты и совместимость

Аналог проверки real/complex из `GraphCompiler` в dsp-flow, но по протоколам и ролям.

Каждый тип блока объявляет порты:

```ts
ports: {
  in:  [{ id: 'http', protocols: ['http','grpc'], role: 'serve' }],
  out: [{ id: 'db',   protocols: ['sql'],          role: 'call'  },
        { id: 'cache',protocols: ['redis'],        role: 'call'  }]
}
```

Матрица совместимости (фрагмент):

| Источник \ Приёмник | LB/L7 | Service | SQL | Cache | Broker | S3 | External |
|---|---|---|---|---|---|---|---|
| Client | ✅ http | ⚠ прямой доступ (антипаттерн) | ⛔ | ⛔ | ⛔ | ✅ (pre-signed) | ✅ |
| LB/L7 | ✅ | ✅ | ⛔ | ⛔ | ⛔ | ✅ (origin) | ⛔ |
| Service | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |
| Broker | ⛔ | ✅ (pull) | ⛔ | ⛔ | ✅ (bridge) | ⛔ | ⛔ |
| SQL | ⛔ | ⛔ | ✅ (репликация) | ⛔ | ✅ (CDC) | ✅ (бэкап) | ⛔ |

* ✅ — разрешено;
* ⚠ — разрешено, но `RuleEngine` выдаст Finding-антипаттерн;
* ⛔ — ошибка компиляции с понятным объяснением («Kafka не может вызвать балансировщик — брокер не
  инициирует HTTP-вызовы; вероятно, вы хотели поставить консьюмер»).

**Два входа у вычислительных блоков.** Строка `Broker → Service ✅ (pull)` из матрицы держится на
том, что серверный блок объявляет не один входной порт, а два: `in` с ролью `serve` принимает
синхронный вызов (`http`, `grpc`, `ws`, `internal`), а `consume` с ролью `consume` — события
брокера (`kafka`, `amqp`, `sqs`, `stream`). Роль порта, а не тип блока, решает и форму ребра:
`shapeFor` видит у источника роль `emit` и ставит `kind: async`, `pull: true`. Так устроены
`service`, `monolith`, `bff`, `serverless`, `ml-inference`, `edge-function`, `webrtc-sfu`;
у `worker`, `batch`, `stream-processor`, `transcoder` и `search-indexer` вход только
консьюмерский. Разделение оставляет честной семантику `serve`: сервис не обслуживает протокол
Kafka как сервер, он его потребляет.

Протокол `stream` носят все потоковые логи — `kinesis`, `nats`, `redis-streams`. Redis Streams
именно поток, а не вызов кэша: совпадение с протоколом `redis` сделало бы его приёмниками
`redis`, `memcached` и `hazelcast` и не дало бы подключить ни одного консьюмера.

**Направление стрелки — конвенция:** стрелка всегда указывает **в сторону движения данных запроса**.
Для sync-вызова это совпадает с направлением вызова. Для брокера — `Producer → Broker → Consumer`,
хотя технически консьюмер тянет данные сам; такое ребро помечается `pull: true` и в модели
инициатором считается приёмник.

## 5. Визуальное кодирование трафика

Развитие приёма из dsp-flow, где `ComplexSignalEdge` рисуется двумя пунктирами со смещением ±2.5 px.

### 5.1. Таблица кодирования

| Признак | Кодирует | Диапазон |
|---|---|---|
| **Толщина** | RPS (логарифм) | `w = clamp(1 + 1.6·log10(rps), 1, 8)` px |
| **Число жил** | 1 — однородный трафик; 2 — смешанный (верхняя read, нижняя write) | смещение ±2.5 px |
| **Цвет жилы** | read `#38bdf8`, write `#f59e0b`, replication `#a78bfa`, event/async `#34d399`, blob/stream `#94a3b8`, batch `#64748b` | CSS-переменные, темы |
| **Прозрачность жилы** | Доля этого профиля в общем трафике (жила с 2% write — почти прозрачная) | 0.25–1.0 |
| **Штрих** | sync — сплошная; async — `5 5`; batch — `12 4 2 4`; replication — двойная сплошная | |
| **Анимация** | Бегущий пунктир, период ∝ 1/throughput(МБ/с); стоп при паузе симуляции | 0.2–3 с |
| **Красный отлив** | ρ приёмника > 0.8; при ρ ≥ 1 — пульсация + «отскакивающие» частицы = дропы | |
| **Значки в середине** | ⏱ таймаут сработал, ↻ ретраи > 5%, ⚡ брейкер открыт, 🔒 идемпотентно, ⧗ лаг очереди | |
| **Подпись (X-ray)** | `↑ 12.4k rps · ↓ 3.1k rps · 4.2 MB/s · p99 8 ms` | включается тумблером |
| **Тип нагрузки** | `HTTP`, `gRPC`, `SQL`, `Kafka` — моноширинной плашкой в подписи связи | виден с того же зума, что и подпись; режим показа — §5.3 |

**Насыщение толщины.** Формула абсолютная, поэтому при `rps ≳ 24 000` она упирается в потолок
8 px и перестаёт различать рёбра. Это осознанная цена: абсолютная шкала делает легенду
«толщина ↔ RPS» сравнимой между схемами, а относительная нормировка по максимуму в схеме — нет.

### 5.2. Правила читаемости

* Максимум **2 визуальные жилы** независимо от числа профилей: остальные агрегируются в «прочее» и
  видны только в X-ray и инспекторе.
* При зуме < 0.5 анимация и подписи отключаются (производительность и шум).
* Состав подписи — имя связи, тип нагрузки, оба сразу или ничего — выбирается настройкой (§5.3).
* При наведении на ребро — подсветка всего Flow, к которому оно относится, и затемнение остальных.
* Толщина считается по **пиковому** сценарию, если выбран режим «показывать пик»; иначе по текущему.

### 5.3. Что писать на линии

Подпись связи состоит из двух статических частей — имени от игрока (`label`) и плашки типа
нагрузки (`protocol`) — и метрик, которые живут отдельно и включаются тумблером «рентген».
Статическую часть выбирает настройка «Подписи связей» в диалоге настроек:

| Режим | Что на линии |
|---|---|
| `both` (по умолчанию) | имя и тип нагрузки |
| `name` | только имя связи |
| `protocol` | только плашка типа нагрузки |
| `off` | ничего: линия остаётся голой |

Это настройка **интерфейса**, а не схемы: она лежит в `sd-preferences` рядом с миникартой и
тепловой картой, общая для всех схем и в файл схемы не попадает — иначе один и тот же режим показа
уезжал бы вместе со схемой к другому игроку. Режим не трогает метрики: `off` при включённом
рентгене оставляет на линии цифры трафика, потому что рентген — отдельный осознанный жест.
Развилку считает чистая функция `edgeLabelParts` в `utils/edgeLabel.ts`, а не сам компонент ребра.

Смысл настройки — плотные схемы. Тип нагрузки проставляется каждому ребру автоматически, поэтому
на схеме из полусотни блоков плашки образуют сплошной шум поверх линий; `off` или `name` возвращают
читаемость, не заставляя чистить поля в инспекторе.

### 5.4. Легенда

Панель легенды внизу палитры (как `SignalLegend` в dsp-flow) — образцы всех типов линий с
подписями, плюс шкала «толщина ↔ RPS».

## 6. Особые типы рёбер

| Тип | Семантика в модели |
|---|---|
| `sync` | Входит в цепочку latency вызывающего. Таймаут и ретраи применяются |
| `async` | Разрывает цепочку latency. Порождает backlog и lag. У приёмника считается `completionTime` |
| `replication` | Не порождается пользовательским трафиком напрямую: λ = λ_write источника × RF. Даёт межзональный/межрегиональный трафик и его стоимость. `sync` репликация добавляет RTT к latency записи |
| `stream` | Непрерывный поток (видео, WebRTC): измеряется в Мбит/с, а не в RPS; ёмкость считается по полосе |
| `cdc` | Поток изменений из БД: λ = λ_write, добавляет лаг |
| `batch` | Периодический перенос: `sizeGb` за `windowHours`, создаёт всплеск нагрузки в окне |
| `pull` (флаг) | Инициатор — приёмник (консьюмер тянет из брокера) |

## 7. UX работы со связями

1. **Создание.** Тянем от выходного порта к входному. Во время перетаскивания подсвечиваются только
   совместимые порты (как в dsp-flow с real/complex).
2. **Дефолты.** Профиль вызова автоматически заполняется из типов блоков: `Service → Redis`
   получает `read 95 / write 5`, protocol `redis`, payload 200/2000 байт; `Service → Kafka` —
   `publish`, kind `async`. Если источник — клиентский блок, размеры запроса и ответа берутся из
   его `avgRequestKb` / `avgResponseKb` **в момент создания ребра**. Дальше по цепочке payload не
   наследуется: каждое ребро несёт свой, иначе один параметр клиента описывал бы и видео-чанк, и
   JSON-ответ API.
3. **Правка.** Клик по ребру → инспектор ребра: подпись, характер связи, тип нагрузки, режим смеси,
   ползунки долей вызовов, политика. Подпись рисуется на холсте посередине ребра при зуме от 0.5 и
   выше; в режиме «рентген» она встаёт в тот же ярлык слева от метрик, а не спорит с ними за место.
   У каждого поля есть подсказка — та же кнопка «Описания», что и у параметров блока, разворачивает
   их под полями, а наведение на подпись показывает то же самое тултипом. Подсказки объясняют не
   значение поля, а его последствие: чем `async` отличается от `sync` в задержке, что делает режим
   «Наследуется», почему повторы без идемпотентности плодят дубликаты.
4. **Быстрые действия** (контекстное меню ребра): «Сделать асинхронным», «Разделить на read/write»,
   «Добавить ретраи», «Добавить circuit breaker», «Вставить блок в разрыв» (например воткнуть кэш
   между сервисом и БД одним кликом — ребро разрезается, кэш встраивается).
5. **Валидация в реальном времени:** как только начали тянуть связь, совместимые порты остальных
   блоков загораются зелёным, несовместимые гаснут до 20% непрозрачности, а порт под курсором
   подтверждает совместимость заливкой. Красного пунктирного ребра с тултипом на несовместимый
   протокол пока нет: подсветка портов гасит попытку раньше, чем ребро появится.

## 8. Заметки по реализации

* Кастомные компоненты рёбер по образцу `RealSignalEdge` / `ComplexSignalEdge`:
  `TrafficEdge` (универсальный, 1–2 жилы), `AsyncEdge`, `ReplicationEdge`, `StreamEdge`.
* Путь — `getBezierPath` (как в dsp-flow) либо `getSmoothStepPath` для «ортогонального» стиля;
  стиль переключается в настройках.
* Анимация — CSS `stroke-dashoffset` + `animation-duration`, **не** requestAnimationFrame: 300+ рёбер
  анимируются GPU-композитингом без нагрузки на JS.
* Невидимая широкая `path` (stroke-width 20, transparent) для попадания мышью — приём уже
  используется в `ComplexSignalEdge`.
* Метки рёбер (`EdgeLabelRenderer`) рендерятся только для видимой области и при зуме ≥ 0.5.
