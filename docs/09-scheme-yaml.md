# 09. Гайд: YAML-формат схемы и задания

Приложение к [PRD.md](../PRD.md). Справочник по тексту, который принимает конструктор заданий:
как описать схему списками `nodes` и `links`, какие поля есть у задания целиком, какое подмножество
YAML понимает разборщик и что означает каждое сообщение об ошибке.

Смежные документы: режим заданий и приёмка — [docs/04-challenges.md](04-challenges.md) (формат ТЗ
в §2, DSL требований в §3, сам конструктор в §12), семантика связей и портов —
[docs/03-connections.md](03-connections.md), каталог типов блоков —
[docs/01-components.md](01-components.md).

## 1. Где встречается YAML

**Только в конструкторе заданий.** Панель «Задания» → вкладка «Свои задания» → «Новое задание».
Задания каталога — TypeScript-модули (решение **D3**), схема на холсте хранится и шарится в JSON
(`SchemeV1`, [docs/05-architecture.md](05-architecture.md) §4), а YAML появился в фазе 4 как
авторский вход: текст, который пишет человек и проверяет приложение.

Одно и то же задание можно писать **в YAML или в JSON** — формат один, разборщик выбирается по
первому непробельному символу: `{` уходит в `JSON.parse`, всё остальное разбирает YAML-читалка.
Поэтому сериализованное задание можно скормить обратно без потерь.

Кнопки редактора:

| Кнопка | Что делает |
|---|---|
| **Шаблон** | Заменяет текст на заготовку со всеми обязательными полями |
| **Схема с холста** | Дописывает в конец блок `starter:` из текущей схемы |
| **Из файла** | Открывает `.yaml`, `.yml`, `.json` и подставляет текст **без проверки** |
| **В файл** | Скачивает текст как есть; имя файла — `<id сохранённого задания>.yaml`, у нового всегда `challenge.yaml` |
| **Проверить** | Разбирает и проверяет, показывает **список** проблем с путями до полей |
| **Сохранить** | То же самое плюс запись в браузер; при ошибке диалог остаётся открытым |

Проверенное задание запускается тем же движком приёмки, что и каталог: те же требования, та же
рубрика, те же звёзды.

## 2. Схема внутри задания

Схема описывается **данными**, а не кодом: списками `nodes` и `links`. В `Challenge` у каталога на
этом месте стоят функции, собирающие `SchemeV1`; в авторском задании функции быть не может — вход
недоверенный.

Схем в задании может быть несколько: обязательная стартовая `starter` и по одной у каждого
эталонного решения (`referenceSolutions[].scheme`). Грамматика у них общая.

```yaml
starter:
  nodes:
    - { id: users, type: client-web, params: { dau: 2000000, peakFactor: 3 } }
    - { id: edge, type: cdn }
    - { id: api, type: service, params: { instances: 4 } }
  links:
    - { from: users, to: edge }
    - { from: edge, to: api, readShare: 0.95 }
```

### 2.1. Узел

| Поле | Тип | Обяз. | Смысл |
|---|---|---|---|
| `id` | Идентификатор: латиница, цифры, дефис, подчёркивание, начинается с буквы | да | Он же подпись узла: имена узлов ключуются идентификатором (ADR-14) |
| `type` | Идентификатор блока из каталога | да | Проверяется по реестру; неизвестный тип — ошибка `unknown-type` |
| `params` | Набор скаляров (число, строка, да/нет) | нет | Накладывается поверх значений по умолчанию блока |
| `parentId` | Строка | нет | Вложенность в контейнер (`region`, `az`, `vpc`, `k8s-cluster`) |
| `position` | `{ x, y }` | нет | Обе координаты обязаны быть числами, иначе поле молча выбрасывается |
| `size` | `{ width, height }` | нет | Имеет смысл у контейнеров; тоже «оба числа или ничего» |

Чего у узла **нет**: `label`, `mirrorOf` и прочие поля `SchemeNode`. Лишние ключи просто
игнорируются.

Что происходит при сборке: `params` мержатся с `defaultParams` блока (ваши значения побеждают),
а узел без `position` встаёт в ряд с шагом 220 px по горизонтали. Имена параметров **не
проверяются**: `params: { zzz: 1 }` пройдёт молча — в отличие от миграции сохранённых схем, которая
чужой параметр выбрасывает.

### 2.2. Связь

| Поле | Тип | Обяз. | Смысл |
|---|---|---|---|
| `from`, `to` | Идентификаторы узлов этой же схемы | да | Висячий конец — ошибка `unknown-node` |
| `weight` | Число | нет | Вес ветвления при разветвлении потока |
| `readShare` | Число 0…1 | нет | Перераспределяет доли профилей: `read`, `scan`, `consume` делят `readShare`, остальные — остаток |
| `calls` | `{ requestBytes, responseBytes, fanout }` | нет | Накладывается на **каждый** профиль ребра |
| `policy` | `{ timeoutMs, retries, circuitBreaker, idempotent }` | нет | Политика вызова; неуказанные поля берутся из умолчания |

**Больше у связи полей нет, и это главное, что нужно понять про формат.** Ни `kind`, ни `protocol`,
ни ручки портов, ни `pull`, ни `mixMode` из задания задать нельзя — их выводит сборщик схемы по
типам блоков:

* **пара портов** — первая совместимая: перебираются выходы источника и входы приёмника, берётся
  первая пара с общим протоколом. Нет общего протокола — схема не собирается, и вы получите
  `scheme-build-failed` с текстом «Несовместимые порты: A → B»;
* **протокол ребра** — первый общий протокол этой пары;
* **форма ребра** — по роли выходного порта и группе приёмника: `replicate` → репликация с профилем
  `transfer`; `emit` → асинхронное ребро с `pull` и профилем `consume`; приёмник группы `messaging`
  → `publish`; группы `observability` → `transfer`; проба → пустой список вызовов; всё остальное →
  синхронное ребро с парой профилей `read`/`write`;
* **смесь и размеры payload по умолчанию** — по группе приёмника: `cache` 95 % чтений и 200 → 2000
  байт, `storage` 80 % и 1000 → 500 000 байт, прочие хранилища 90 % и 300 → 4000 байт, остальные
  90 % и 500 → 2000 байт;
* **политика по умолчанию** — таймаут 1000 мс, 0 повторов, без предохранителя, не идемпотентно.

Отсюда практическое следствие: **`calls` накладывается сразу на все профили ребра**, поэтому задать
раздельно «чтение 300 байт, запись 4 КБ» одной связью нельзя. Нужна разная физика — разводите
потоки на разные рёбра или правьте схему на холсте.

### 2.3. Кнопка «Схема с холста»

Дописывает в конец текста блок `starter:` из того, что сейчас на холсте. Выгружаются **только**:
идентификатор, тип, округлённая позиция и параметры, **отличающиеся от умолчаний блока** — иначе
фрагмент был бы нечитаемым. Связи выгружаются как `{ from, to }`.

Что при этом теряется и что придётся дописать руками: `parentId` и `size` (то есть вложенность в
регионы, зоны и кластеры), а у рёбер — веса, смесь, размеры вызовов и политика. Настройки схемы
(`settings`) не выгружаются и в задании не читаются вообще: авторское задание всегда считается в
канонических условиях приёмки.

## 3. Задание целиком

Минимальное валидное задание — семь полей:

```yaml
id: my-challenge
level: 2
estimatedMinutes: 30
title: Моё задание
brief: Что за система, какая нагрузка и что важно проверить.
flows:
  - { id: users, name: Просмотр, weightInScore: 1 }
requirements:
  - id: R1
    kind: budget
    desc: Стоимость не выше $50 000 в месяц
    maxMonthlyCostUsd: 50000
starter:
  nodes:
    - { id: users, type: client-web }
  links: []
```

Полный список ключей верхнего уровня:

| Ключ | Тип | Обяз. | Если не указан | Правила |
|---|---|---|---|---|
| `id` | Идентификатор | да | — | Латиница, цифры, дефис, подчёркивание; начинается с буквы |
| `level` | Число | да | — | 1…5, целое |
| `estimatedMinutes` | Число | да | — | 1…600 |
| `title` | Текст или `{ ru, en }` | да | — | Одна строка = оба языка; можно указать только один язык, второй зеркалится |
| `brief` | Текст или `{ ru, en }` | да | — | Обычно многострочный блочный скаляр |
| `starter` | Схема | да | — | См. §2 |
| `flows` | Список потоков | да, ≥ 1 | — | `id` (совпадает с id узла стартовой схемы), `name`, `weightInScore` 0…1 |
| `requirements` | Список требований | да, ≥ 1 | — | См. §4 |
| `bonusObjectives` | Список требований | нет | `[]` | Тот же формат, что у `requirements` |
| `tags` | Список строк | нет | `[]` | Метки в карточке задания |
| `given` | Набор «число или строка» | нет | `{}` | Витрина исходных данных в панели; на расчёт не влияет |
| `constraints` | `{ maxNodes, allowedGroups, forbiddenTypes }` | нет | `{}` | Группы и типы проверяются по реестру |
| `scenarios` | `{ required, bonus }` | нет | пусто | Списки идентификаторов сценариев |
| `relaxation` | Набор «сценарий → послабления» | нет | `{}` | `latencyFactor`, `utilizationFactor`, `availabilityFloor` |
| `requiredConsistencyModel` | Строка | нет | не задано | Единственное значение — `anomalies` |
| `lockedParams` | Набор «узел → параметры» | нет | `{}` | Значения, которые игрок менять не должен |
| `hints` | Список подсказок | нет | `[]` | `level` 1…3, `cost` ≥ 1, `text`, необязательный `forRequirement` |
| `referenceSolutions` | Список эталонов | нет | `[]` | `id`, `name`, `tradeoff`, `scheme` |

**Ключей больше нет.** Всё незнакомое проверка молча пропускает — в том числе опечатки в именах
полей: написав `requirments:`, вы получите не «неизвестный ключ», а две жалобы на пустое место —
«ожидается список» и «нужно хотя бы одно требование» по пути `requirements`. Профиль цен из задания
не задаётся: приёмка всегда считает по каноническому профилю и фиксированному сиду.

### 3.1. Потоки

```yaml
flows:
  - id: users
    name: { ru: Просмотр ленты, en: Feed browsing }
    weightInScore: 1
```

`flows[].id` обязан совпадать с идентификатором узла стартовой схемы — иначе `flow-without-node`.
Но проверка на этом заканчивается, а движок требует большего: поток появится, только если этот узел
из группы `clients` **и у него есть исходящая связь** с ненулевым RPS. Иначе требования по потоку
приедут со статусом «неизвестно» и причиной «поток не найден» — без единой ошибки на этапе проверки.

`weightInScore` валидируется (0…1), но на приёмку не влияет: это подпись «вес в оценке» в панели.

### 3.2. Сценарии и послабления

```yaml
scenarios:
  required: [peak]
  bonus: [az-failure, spike]

relaxation:
  peak: { utilizationFactor: 1.1 }
```

Допустимые идентификаторы (17): `baseline`, `peak`, `spike`, `growth`, `black-friday`,
`az-failure`, `region-failure`, `db-failover`, `cache-flush`, `thundering-herd`, `hot-key`,
`slow-dependency`, `retry-storm`, `poison-message`, `stale-read`, `write-conflict`, `split-brain`.

`scenarios.required` — вторая звезда: схема обязана держать эти сценарии. `relaxation` смягчает
пороги в конкретном сценарии: `latencyFactor` растягивает целевую задержку, `utilizationFactor` —
допустимую загрузку, `availabilityFloor` задаёт нижнюю планку доступности.

### 3.3. Запертые параметры

```yaml
lockedParams:
  users:
    dau: 2000000
    peakFactor: 3
```

Это исходные данные, которые игрок не должен «подкрутить»: Realism Gate сравнивает их **строго** и
выдаёт нарушение, если значение изменилось или узел удалён. Ключ верхнего уровня — идентификатор
узла стартовой схемы (проверяется), а вот имена параметров не проверяются: запертый несуществующий
параметр даст вечное нарушение, которое игрок не сможет починить.

### 3.4. Подсказки

```yaml
hints:
  - level: 1
    cost: 5
    text: { ru: С чего начать разбор нагрузки?, en: Where would you start reading the load? }
    forRequirement: R1
```

`level` — 1…3 (чем выше, тем конкретнее), `cost` — штраф в баллах рубрики. `forRequirement` может
ссылаться **только на `requirements`**: ссылка на идентификатор бонусной цели даст
`unknown-requirement`.

## 4. Требования

Общие поля любого требования: `id` (идентификатор), `kind` (один из тринадцати видов), `desc`
(текст или пара `ru`/`en`) и необязательный `scenario`.

| `kind` | Обязательные поля | Необязательные | Значения |
|---|---|---|---|
| `capability` | `flow`, `to` | `viaAny`, `notVia`, `asyncBefore` | Указатель на блок: `{ group }`, `{ type }` или оба; пустой указатель — ошибка |
| `slo` | `flow`, `metric`, и хотя бы один из `max` / `min` | второй порог | `metric`: `latency.p50`, `latency.p95`, `latency.p99`, `availability`, `errorRate` |
| `capacity` | `maxUtilization` | — | 0…1 |
| `durability` | `flow`, `minReplication` | — | `minReplication` ≥ 1 |
| `redundancy` | `flow`, `minRedundancy` | `spanAzs` | Оба ≥ 1 |
| `budget` | `maxMonthlyCostUsd` | — | ≥ 0 |
| `storage` | `horizonYears`, `headroom` | — | `headroom` ≥ 1 |
| `freshness` | `maxLagSec` | — | ≥ 0 |
| `consistency` | `flow`, `requires` | — | `strong`, `read-your-writes`, `eventual` |
| `anomaly` | `code`, и хотя бы один из `maxRatePerSec` / `maxSharePercent` | второй порог | `code` — один из одиннадцати, см. ниже |
| `geo` | Хотя бы одно из `minRegions`, `maxClientRttMs`, `residency` | остальные | `minRegions` ≥ 1 |
| `rpo-rto` | `maxRpoSec`, `maxRtoSec` | — | Оба ≥ 0 |
| `security` | `requires` (список) | — | `auth-on-edge`, `no-direct-client-to-db`, `tls-terminate`, `rate-limit-at-edge` |

Коды аномалий: `stale-read`, `read-your-writes`, `monotonic-read`, `lost-update`, `write-conflict`,
`lost-write-lww`, `duplicate-processing`, `ordering-violation`, `dirty-read`,
`non-repeatable-read`, `phantom-read`.

Смысл каждого вида разобран в [docs/04-challenges.md](04-challenges.md) §3; здесь — только форма
записи. Четырнадцатого вида, `custom`, в авторском формате нет и не будет: произвольная функция не
сериализуется, а исполнять выражение из недоверенного текста в статическом приложении — значит
спроектировать язык выражений, которого нет ни в одном документе.

```yaml
requirements:
  - id: R1
    kind: slo
    desc: { ru: p99 не выше 250 мс, en: p99 stays under 250 ms }
    flow: users
    metric: latency.p99
    max: 250
  - id: R2
    kind: capability
    desc: { ru: Чтения идут через кэш, en: Reads go through a cache }
    flow: users
    to: { group: sql }
    viaAny: [{ group: cache }]
  - id: R3
    kind: capacity
    desc: Ни один блок не загружен выше 80%
    maxUtilization: 0.8
    scenario: peak
```

Две тонкости приёмки, которые видно только в коде:

* **`min` у `slo` осмыслен практически только для `availability`.** У задержек цель считается от
  `max`, и требование с одним лишь `min` получит цель 0 — выполнить его нельзя.
* **Требование с `scenario` проверяется только в этом сценарии**, и попадёт в прогон, лишь если
  сценарий указан в `scenarios.required` или `scenarios.bonus`. При этом в любом прогоне сценария
  дополнительно проверяются все требования видов `slo` и `capacity`, независимо от их `scenario`.

Идентификаторы требований и бонусных целей уникальны сквозным списком: повтор даёт
`duplicate-requirement-id`.

## 5. Подмножество YAML

Разборщик свой (`src/engine/authoring/yaml.ts`), около 300 строк без зависимостей: тянуть в бандл
полноценный YAML ради авторского режима не стали. Из этого следуют и возможности, и ограничения.

### 5.1. Что поддерживается

| Что | Пример |
|---|---|
| Наборы полей с отступами | `title:` → `  ru: Моё задание` |
| Списки, в том числе с наборами внутри | `- id: R1` + следующей строкой `  kind: slo` |
| Потоковые списки и наборы, вложенные | `tags: [cache, cost]`, `desc: { ru: …, en: … }` |
| Числа с подчёркиваниями, дроби, экспонента | `1_000_000`, `0.25`, `1e3` |
| Логические значения и пустота | `true`/`false`, `yes`/`no`, `on`/`off`, `null`, `~`, пустое значение |
| Строки в кавычках, одинарных и двойных | `'да: нет'`, `"перенос\nстроки"` |
| Блочные скаляры `\|` и `>` с отсечением `-` | Многострочный `brief` |
| Комментарии и разделитель документа | `# текст`, `---` |
| JSON целиком | Текст, начинающийся с `{` |

Регистр в литералах не важен: `TRUE`, `Yes`, `Null` работают. Кавычки отменяют распознавание типа:
`"1000"` останется строкой.

### 5.2. Что не поддерживается

Якоря `&`, ссылки `*`, теги `!`, директивы `%`, сохраняющее отсечение `|+`, индикатор отступа
(`|2`), несколько документов в файле, многострочные потоковые конструкции, блочный список внутри
блочного списка и **отступ табуляцией** (в YAML только пробелы — здесь это жёсткая ошибка в любой
строке, включая тело блочного скаляра). На каждый такой случай разборщик возвращает код ошибки и
номер строки, а не падает.

### 5.3. Отклонения от спецификации, о которых надо знать

Это не полный YAML, и в шести местах он ведёт себя иначе. Все шесть — реальные грабли:

1. **Список пишется с отступом относительно своего ключа.** Классический YAML разрешает `flows:` и
   `- id: users` в одной колонке — здесь это ломает разбор. Пишите так, как в шаблоне:
   ```yaml
   flows:
     - id: users
   ```
2. **Соседние ключи одного набора должны совпадать по колонке точно.** Величина отступа любая
   (хоть один пробел), но «поехавший» на пробел ключ — ошибка `bad-indent`.
3. **`---` — это не разделитель документов, а пустая строка.** Два «документа» в одном файле
   сольются в один набор, а совпавшие ключи дадут `duplicate-key`. Маркер `...` не поддержан вовсе.
4. **Хвостовые пустые строки блочного скаляра срезаются всегда**, даже у `|`. Поэтому `brief` не
   тащит за собой пустую строку.
5. **Комментарий отдельной строкой внутри блочного скаляра теряет текст** и превращается в пустую
   строку. Хвостовой комментарий на содержательной строке при этом сохраняется как часть текста.
6. **Незакрытая кавычка не считается ошибкой**: `title: "Моё задание` разберётся в строку вместе с
   кавычкой. Ждать здесь диагностики не стоит.

Плюс две мелочи про скаляры: дубли ключей внутри `{ … }` молча перетираются последним значением
(в блочном наборе это ошибка), а `+3`, `.5`, `5.` и `0x10` числами **не** считаются — это строки.

## 6. Ошибки

Проверка возвращает **список** проблем, а не первую попавшуюся. У каждой — путь до поля и код,
который интерфейс превращает в человеческий текст.

Путь бывает трёх видов: `root` для корня, точечная адресация с индексами
(`requirements[3].requires[1]`, `starter.nodes[0].params.zzz`, `lockedParams.users`) и
`line N` — так помечаются ошибки самого разбора текста, где до полей дело ещё не дошло.

**Ошибки разбора текста:**

| Код | Что случилось |
|---|---|
| `tab-indent` | Отступ табуляцией: в YAML только пробелы |
| `bad-indent` | Сбит отступ |
| `expected-key` | Ожидается «поле: значение» |
| `empty-key` | Пустое имя поля |
| `duplicate-key` | Поле повторяется |
| `unbalanced-flow` | Не закрыта скобка `[` или `{` |
| `bad-escape` | Неизвестная escape-последовательность в двойных кавычках |
| `unsupported-yaml` | Якоря, ссылки и теги не поддерживаются |
| `unsupported-chomping` | Поддерживаются только `\|`, `\|-`, `>`, `>-` |
| `bad-json` | Текст начинается с `{`, но JSON не разбирается |
| `unparsable` | Текст не разбирается |

**Ошибки проверки задания:**

| Код | Что случилось |
|---|---|
| `expected-mapping` | Ожидается набор полей |
| `expected-list` | Ожидается список |
| `expected-text` | Ожидается непустая строка |
| `expected-slug` | Идентификатор: латиница, цифры, дефис и подчёркивание, начинается с буквы |
| `expected-number` | Ожидается число в диапазоне (границы названы в сообщении) |
| `expected-localized` | Ожидается текст или пара `ru`/`en` |
| `expected-param-value` | Ожидается число, строка или да/нет |
| `unknown-value` | Недопустимое значение; допустимые перечислены в сообщении |
| `unknown-group` | Нет такой группы блоков |
| `unknown-type` | Нет такого блока |
| `unknown-node` | Нет такого узла в стартовой схеме |
| `unknown-flow` | Нет такого потока |
| `unknown-requirement` | Нет такого требования |
| `empty-matcher` | Нужно указать `group` или `type` |
| `slo-without-threshold` | У требования `slo` нужен `max` или `min` |
| `anomaly-without-threshold` | У требования `anomaly` нужен `maxRatePerSec` или `maxSharePercent` |
| `geo-without-target` | У требования `geo` нужен `minRegions`, `maxClientRttMs` или `residency` |
| `duplicate-node-id` | Идентификаторы узлов повторяются |
| `duplicate-requirement-id` | Идентификаторы требований повторяются |
| `flow-without-node` | Поток должен совпадать с идентификатором узла стартовой схемы |
| `no-flows` | Нужен хотя бы один поток |
| `no-requirements` | Нужно хотя бы одно требование |
| `scheme-build-failed` | Схема не собирается; причина — в тексте сообщения |
| `incomplete` | Не хватает обязательных полей (защитная ветка: обычно проблема названа точнее) |

Деления на «ошибки» и «предупреждения» нет: любая проблема блокирует сохранение.

**Схема проверяется сборкой.** Последним шагом разбора схема действительно собирается тем же
кодом, что и на холсте, поэтому несовместимость портов ловится в редакторе, а не при открытии
задания. Сообщения внутри `scheme-build-failed` два: «Нет узла для связи A → B» и «Несовместимые
порты: A → B». Висячий конец связи обычно даёт сразу две проблемы — `unknown-node` на самом поле и
`scheme-build-failed` на схеме.

## 7. Хранение и запуск

Задания лежат в браузере, в `localStorage` под ключом `sd-authored`, и хранится **исходный текст**,
а не восстановленный из структуры: правка открывает ровно то, что вы написали, с комментариями и
форматированием. Рядом лежат идентификатор, заголовок (русский) и время последнего сохранения.

* **Совпадение `id` перезаписывает** ранее сохранённое задание без вопросов — это же и способ
  «обновить» задание.
* Ограничения на количество нет; на весь массив действует общий предел записи в 4 МБ.
* Прогресс и звёзды по авторским заданиям хранятся отдельно, ключом `authored:<id>`, и попадают в
  общую выборку прогресса наравне с каталогом и наборами практики.
* Запуск идёт через тот же воркер приёмки: ссылка вида «авторское задание + разобранная
  спецификация» уходит в движок наравне со ссылками на каталог. Если сохранённый текст перестал
  разбираться (например, вы редактировали его в файле и импортировали обратно), задание не
  запустится — откроется редактор со списком проблем.

Перенести задание на другую машину можно только файлом: «В файл» → «Из файла». Обмена через сервер
нет — community-задания требуют бэкенда и доверенного источника импорта, и в списке
нереализованного они и остаются.

## 8. Грабли

| Симптом | Причина |
|---|---|
| «Нужно хотя бы одно требование», хотя они есть | Опечатка в имени ключа верхнего уровня — незнакомые ключи игнорируются молча |
| Требование всегда «неизвестно» | Поток не появился: узел не из группы `clients` либо у него нет исходящей связи |
| Задание непроходимо с первого шага | `constraints.maxNodes` меньше, чем узлов в стартовой схеме |
| Требование `slo` не выполняется ни при каких числах | Задан только `min` у метрики задержки — цель считается от `max` |
| Требование со `scenario` никогда не проверяется | Сценарий не указан в `scenarios.required` или `scenarios.bonus` |
| Realism Gate ругается на параметр, которого не видно | В `lockedParams` заперт параметр, которого у блока нет |
| Вложенность в регион пропала после «Схемы с холста» | Выгрузка не пишет `parentId` и `size` — допишите руками |
| Настройки схемы игнорируются | `starter.settings` не читается: приёмка всегда идёт в канонических условиях |
| Разные размеры чтения и записи не получаются | `calls` накладывается на все профили ребра сразу |
| Текст из блочного скаляра потерялся | Строка-комментарий внутри `\|` превращается в пустую строку |
| Ошибка на строке, которая выглядит правильной | Скорее всего отступ: табуляция, список в колонке ключа или сдвинутый сосед |

## 9. Полный пример

Шаблон из редактора («Шаблон») — рабочее задание, которое проходит проверку целиком:

```yaml
id: my-challenge
level: 2
estimatedMinutes: 30
tags: [cache, cost]

title:
  ru: Моё задание
  en: My challenge

brief:
  ru: |
    Опишите задачу: что за система, какая нагрузка и что важно проверить.
  en: |
    Describe the task: what the system is, the load it carries and what matters.

given:
  dau: 2000000
  peakFactor: 3

flows:
  - id: users
    name: { ru: Просмотр, en: View }
    weightInScore: 1

constraints:
  maxNodes: 10
  allowedGroups: [clients, edge, compute, cache, sql, storage, topology]

requirements:
  - id: R1
    kind: slo
    desc: { ru: p99 не выше 250 мс, en: p99 stays under 250 ms }
    flow: users
    metric: latency.p99
    max: 250
  - id: R2
    kind: capacity
    desc: { ru: Ни один блок не загружен выше 80%, en: No block runs hotter than 80% }
    maxUtilization: 0.8
  - id: R3
    kind: budget
    desc: { ru: Стоимость не выше $50 000 в месяц, en: Monthly cost stays under $50k }
    maxMonthlyCostUsd: 50000

bonusObjectives:
  - id: B1
    kind: slo
    desc: { ru: Медиана укладывается в 90 мс, en: Median stays under 90 ms }
    flow: users
    metric: latency.p50
    max: 90

scenarios:
  required: [peak]
  bonus: [az-failure]

relaxation:
  peak: { utilizationFactor: 1.1 }

lockedParams:
  users:
    dau: 2000000
    peakFactor: 3

starter:
  nodes:
    - { id: users, type: client-web, params: { dau: 2000000, peakFactor: 3 } }
  links: []

hints:
  - level: 1
    cost: 5
    text: { ru: С чего начать разбор нагрузки?, en: Where would you start reading the load? }
```

Чего в шаблоне нет, хотя формат это поддерживает: `referenceSolutions`,
`requiredConsistencyModel`, `scenario` у требования, `viaAny` / `notVia` / `asyncBefore` у
`capability`, `parentId` и `size` у узлов, `weight` / `readShare` / `calls` / `policy` у связей.
И наоборот: почти всё, что есть в шаблоне, необязательно — минимальный набор показан в §3.
