# 04. Режим заданий и алгоритм приёмки

Приложение к [PRD.md](../PRD.md). Отвечает на вопрос из ТЗ: *«продумать алгоритм приёмки задания —
поскольку в систем-дизайне нет "правильной" схемы»*.

---

## 1. Философия оценки

В System Design нет эталонного графа. Но есть три вещи, которые **проверяемы объективно**:

| Что проверяем | Как |
|---|---|
| **1. Способности (capabilities)** | Может ли система вообще выполнить требуемое? Есть ли путь от «пользователь загружает видео» до долговечного хранилища? Это предикаты над графом, а не сравнение с образцом |
| **2. Числа (numbers)** | Держит ли схема заявленную нагрузку, укладывается ли в SLO, бюджет и объёмы. Это результат симулятора |
| **3. Поведение под стрессом (behaviour)** | Что произойдёт при отказе AZ, всплеске ×5, холодном кэше, горячем ключе. Это батарея сценариев |

Ни одна из трёх проверок не требует «правильной схемы». Именно так работает и живое интервью:
интервьюер не сверяет вашу картинку с эталоном — он **стресс-тестирует** её вопросами.

> **Формула приёмки:** задание считается сданным, если схема *умеет* то, что требуется,
> *выдерживает* заявленные числа и *не разваливается* на сценариях. Красота, элегантность и
> стоимость влияют только на количество звёзд.

## 2. Формат задания

Автору задание пишется в YAML, в рантайме компилируется в JSON.

```yaml
id: video-hosting
level: 3
title:
  ru: Видеохостинг (YouTube-like)
  en: Video hosting (YouTube-like)
estimatedMinutes: 45
tags: [media, cdn, storage, async, cost]

brief:
  ru: |
    Спроектируйте видеохостинг: пользователи загружают видео, они транскодируются
    в несколько качеств и раздаются миллионам зрителей.

given:
  dau: 100_000_000
  viewsPerUserDay: 5
  avgWatchMinutes: 6
  defaultQuality: { label: 1080p, bitrateMbps: 4.5 }
  uploadsPerDay: 50_000
  avgUploadMinutes: 10
  avgSourceSizeGb: 1.5
  retentionYears: 3
  peakFactor: 3

flows:
  - id: watch
    name: { ru: Просмотр видео, en: Watch video }
    entryHint: client-web
    derived: { rps: "dau * viewsPerUserDay / 86400" }
    mix: { read: 0.99, write: 0.01 }
    slo: { p99Ms: 300, availability: 0.9995 }
    weightInScore: 0.6
  - id: upload
    name: { ru: Загрузка видео, en: Upload video }
    derived: { rps: "uploadsPerDay / 86400" }
    mix: { read: 0.0, write: 1.0 }
    slo: { p99Ms: 2000, completionMinutes: 30 }
    weightInScore: 0.4

constraints:
  maxMonthlyCostUsd: 4_000_000
  allowedGroups: [clients, edge, compute, sql, nosql, storage, cache, messaging, olap, observability, topology]
  forbidden: []
  maxNodes: 40

requirements: [ ... ]        # см. §3
scenarios:
  required: [baseline, peak, az-failure, cache-flush]
  bonus:    [hot-key, growth, slow-dependency]

rubric: { ... }              # см. §5
hints: [ ... ]               # см. §7
referenceSolutions: [ ... ]  # см. §8
```

## 3. DSL требований

Требование — предикат над **скомпилированной схемой + результатом симуляции**. Тринадцать базовых
видов покрывают ~95% случаев; четырнадцатый (`custom`) — лазейка для авторов.

| Вид | Что проверяет | Пример |
|---|---|---|
| `capability` | Существует путь от A к B, удовлетворяющий ограничениям | `from: flow:upload, to: group:storage, via_any: [compute:*], not_via: [sql:*]` — «видео должно доехать до объектного хранилища, а не в реляционную БД» |
| `slo` | Метрика Flow в пределах порога при сценарии | `flow: watch, metric: latency.p99, max: 300ms, scenario: baseline` |
| `capacity` | Ни один узел не насыщен | `maxUtilization: 0.8, scenario: peak` |
| `durability` | Путь записи заканчивается в долговечном хранилище | `flow: upload, minReplication: 3` или `durability >= 0.999999999` |
| `redundancy` | Нет SPOF на критическом пути Flow | `flow: watch, minRedundancy: 2, spanAzs: 2` |
| `budget` | Стоимость в пределах лимита | `maxMonthlyCostUsd: 4000000` |
| `storage` | Выделенной ёмкости хватает на горизонт; считаются только блоки, достижимые от клиента, — брошенный на холст Postgres требование не закрывает | `horizonYears: 3, headroom: 1.2` |
| `freshness` | Лаг реплики/очереди в пределах | `edge: cdc:*, maxLagSeconds: 60` |
| `consistency` | Уровень согласованности на пути | `flow: payment, requires: strong` |
| `anomaly` | Частота аномалии согласованности в пределах порога | `flow: checkout, type: lost-update, maxRatePerSec: 0` |
| `geo` | Гео-требования: покрытие, резидентность, локальность | `regions: ">=2", residency: strict, maxClientRttMs: 120` |
| `rpo-rto` | Целевые RPO и RTO при отказе региона | `maxRpoSec: 5, maxRtoSec: 300` |
| `security` | Обязательные контроли на периметре | `requires: [auth-on-edge, no-direct-client-to-db, tls-terminate]` |
| `custom` | Произвольный предикат (чистая функция от `SimulationResult`) | для экзотики |

### 3.0. Требования по аномалиям согласованности

Поскольку симуляция аномалий включена по умолчанию (решение **D2**), задания могут требовать не
объявленный «уровень консистентности», а **наблюдаемое поведение** — что гораздо честнее:

```yaml
  - id: R7
    kind: anomaly
    flow: checkout
    type: lost-update
    maxRatePerSec: 0
    desc: { ru: Баланс не должен теряться при одновременных списаниях }
  - id: R8
    kind: anomaly
    flow: feed
    type: stale-read
    maxSharePercent: 5
    desc: { ru: До 5% устаревших чтений ленты допустимо — это не банк }
  - id: R9
    kind: anomaly
    flow: post-comment
    type: read-your-writes
    maxSharePercent: 0.1
    desc: { ru: Пользователь обязан видеть собственный комментарий сразу }
```

Такая формулировка **не диктует решение**: обнулить `lost-update` можно и через CAS, и через
пессимистичную блокировку, и через single-writer-на-ключ, и через CRDT — все четыре пути пройдут
приёмку, но по-разному отразятся в latency, ёмкости и стоимости, то есть в рубрике.

**Задание может зафиксировать режим модели:** поле `requiredConsistencyModel: anomalies` в YAML
запрещает переключить настройку в `выкл`/`атрибут` на время прохождения — иначе задания про
платежи тривиально «сдаются» отключением модели.

### 3.1. Ключевой принцип: требования — про свойства, не про блоки

**Плохо:** `requires: node type == 'cdn'`
**Хорошо:** `slo: watch.p99 < 300ms` + `budget: egress cost < $X`

Второе неявно заставляет поставить CDN, но не запрещает решить иначе (собственные edge-кэши,
P2P-раздача, региональные origin). Ровно одно исключение: задания-туториалы уровня 1, где
явное требование блока — часть обучения.

### 3.2. Живая обратная связь

Все требования пересчитываются на каждое изменение схемы (debounce 300 мс) и показываются
списком-чеклистом. Требование может быть в одном из состояний:
`не выполнено` / `выполнено` / `выполнено с запасом X%` / `не проверяемо (схема не компилируется)`.

## 4. Конвейер приёмки

```
Нажата кнопка «Сдать»
   │
   ├─[0] Realism Gate ──── схема физически осмысленна? ────► ❌ «Параметры вне реалистичных пределов»
   │
   ├─[1] Compile ───────── граф валиден, все блоки связаны ─► ❌ «Схема не компилируется»
   │
   ├─[2] Hard Gates ────── обязательные requirements при baseline
   │                        ❌ → отчёт «какое требование и почему»
   │
   ├─[3] Scenario Battery ─ прогон required-сценариев
   │                        ❌ → «упало на az-failure: p99 = 1.8 c»
   │
   ├─[4] Lint ──────────── антипаттерны и best practices (баллы, не гейт)
   │
   ├─[5] Rubric ────────── подсчёт баллов по измерениям
   │
   └─[6] Verdict ───────── звёзды 1–3 + отчёт + разблокировка эталонных решений
```

### 4.0. Канонические условия приёмки

Приёмка судит **дизайн**, а не настройки песочницы, поэтому весь конвейер прогоняется в
фиксированных условиях, что бы ни стояло в панели схемы:

| Настройка | В приёмке | Почему |
|---|---|---|
| Выборка Monte-Carlo | 20 000 сэмплов | «Глубина модели» — про отзывчивость интерфейса, а не про строгость оценки |
| Сид | `1` | Иначе один и тот же файл получал бы разное число звёзд от сида: порог требования проходится внутри шума |
| Профиль цен | `aws-2026-q2`, либо объявленный заданием `pricingProfile` | Бюджет задания задан в абсолютных деньгах; переключение профиля на `hetzner` переводило три задания из 0★ в 3★ |
| Сценарий | Свой для каждого требования (§4.3) | Требование объявляет, при каком сценарии оно проверяется |

Эталонные решения прогоняются в тех же условиях — иначе сравнение с ними было бы нечестным.
Остальные настройки схемы (модель согласованности) не подкручиваются, а проверяются: если задание
объявило `requiredConsistencyModel`, ослабленная настройка ловится Realism Gate.

### 4.0.1. Realism Gate (защита от «читерства»)

Без этого шага любое задание сдаётся одним блоком с `maxRpsPerInstance = 10⁹`.

| Проверка | Правило |
|---|---|
| Границы параметров | Каждый параметр блока объявляет `realisticRange`. Выход за границы допустим в песочнице, но блокирует приёмку с пояснением |
| Ручной override производных величин | `cacheHitRatio`, `compressionRatio`, `speedFactor`, заданные вручную выше «правдоподобного», отклоняются |
| Один инстанс на всё | `instances` ограничен `maxRealisticInstances` типа блока |
| Пустые связи | Ребро с `fanout = 0` на критическом пути = разрыв способности |
| Отключённая наблюдаемость ради стоимости | Если задание требует логов — `samplingRate` ограничен снизу |
| Deus ex machina | Блок `external-api` не может обслуживать core-логику задания (проверяется `not_via`) |
| Отключение модели аномалий | Если задание объявило `requiredConsistencyModel`, настройка блокируется на время прохождения |
| Нулевой лаг репликации вручную | `replicaLagMs` ниже физического минимума (RTT/2 соответствующего линка) отклоняется |
| «Регион без содержимого» | Регион-зеркало, в котором нет узлов критического пути, не засчитывается как резерв в предикате `geo` |

Формулировка отказа всегда обучающая: «Postgres на 8 vCPU не выдаёт 500 000 point-read/с; реалистичный
потолок — 20 000. Попробуйте шардирование или кэш».

### 4.2. Hard Gates — примеры вердиктов

Отказ **всегда** сопровождается: нарушенным требованием, фактическим числом, целевым числом, узлом
с наибольшим вкладом и ссылкой «показать на схеме».

```
❌ R4  SLO «watch»: p99 = 486 мс > 300 мс (baseline)
       Вклад по хопам:  CDN 22 мс → API GW 4 мс → Metadata Service 12 мс
                        → Postgres 438 мс  ← ρ = 0.97, ожидание в очереди 402 мс
       Ограничитель Postgres: maxConnections (200) → потолок 4 100 rps при λ = 5 800 rps
       [Показать на схеме]  [Почему так посчитано]
```

### 4.3. Батарея сценариев

`required`-сценарии обязательны для 2 звёзд, `bonus` — для 3-й. Критерий прохождения сценария —
те же `slo` и `capacity`-требования, но с ослабленными порогами, объявленными в задании
(например при `az-failure` допускается p99 ×2 и деградация на 5 минут).

## 5. Рубрика и звёзды

### 5.1. Звёзды

| Звёзд | Условие |
|---|---|
| ☆☆☆ | Не сдано: провален Realism Gate, компиляция или Hard Gates |
| ★☆☆ | Все Hard Gates при `baseline` |
| ★★☆ | + пройдены все `required`-сценарии |
| ★★★ | + рубрика ≥ 80 из 100 баллов |

### 5.2. Измерения рубрики

| Измерение | Вес | Как считается |
|---|---|---|
| **Отказоустойчивость** | 25 | Доля пройденных `bonus`-сценариев + расчётная доступность vs целевая + отсутствие SPOF + переживание `az-failure` и `region-failure` + изоляция отказов (bulkhead, брейкеры) |
| **Корректность данных** | 15 | Частота аномалий по типам относительно порогов задания + осознанность выбора (явная стратегия разрешения конфликтов, RYW там, где он нужен, идемпотентность на at-least-once). Ноль аномалий ценой безумной latency баллов не даёт — смотрится связка |
| **Экономика** | 20 | `100 · clamp(1 − log₂(C_user / C_ref)/2, 0, 1)`, где `C_ref` — стоимость лучшего эталонного решения. Равно эталону → 100, вдвое дороже → 50, вчетверо → 0 |
| **Простота** | 15 | `100 − 6·(неиспользуемые блоки) − 4·max(0, N_user − 1.5·N_ref) − 3·(глубина sync-цепочки > 5)`. Регионы-зеркала считаются как один регион — за мультирегион не штрафуем |
| **Инженерные практики** | 15 | Чеклист положительных правил (§6.1), каждое даёт баллы |
| **Запас прочности** | 5 | Медиана `1 − ρ` по узлам критического пути; переусиление (все ρ < 0.15) тоже штрафуется — это переплата |
| **Бонусные цели задания** | 5 | Явные `bonusObjectives` в YAML («уложись в $2M», «RPO < 1 с», «p99 < 150 мс») |

Сумма весов — ровно 100. Итог показывается **радаром** по семи осям + текстовым разбором каждой оси.

Если модель согласованности выключена настройкой (и задание это разрешает), ось «Корректность
данных» не оценивается, а её вес пропорционально распределяется по остальным.

### 5.3. Штрафы

| За что | Штраф |
|---|---|
| Каждый сработавший антипаттерн (§6.2) | −3…−15 баллов по тяжести |
| Использование подсказки уровня 1 / 2 / 3 | −5 / −10 / −20 баллов |
| Ручной override производной величины | −5 баллов за каждый |
| Попытка сдачи после провала (со 2-й) | −3 балла за попытку, не ниже 0 |

## 6. Линтер архитектуры (RuleEngine)

Аналог `ValidationService` из dsp-flow, но правила предметные. Работает всегда, в том числе в
песочнице (там — как подсказки, без баллов).

### 6.1. Положительные правила (дают баллы)

| Правило | Условие |
|---|---|
| `cache-before-hot-db` | Перед БД с read-heavy трафиком и высоким потенциалом кэширования стоит кэш |
| `cdn-for-static` | Статика/медиа раздаётся через CDN, а не из origin |
| `async-for-slow-work` | Операции > 1 с (транскодинг, отчёты, рассылки) вынесены за очередь |
| `dlq-present` | У каждого консьюмера есть DLQ и ограничение попыток |
| `idempotent-writes` | Ребро с ретраями к write-эндпоинту помечено идемпотентным |
| `rate-limit-at-edge` | На периметре есть ограничение частоты |
| `auth-at-edge` | Аутентификация выполняется на входе, а не в каждом сервисе по-своему |
| `read-replicas` | Read-heavy SQL имеет реплики чтения и чтение туда направлено |
| `multi-az` | Критический путь размазан минимум по 2 AZ |
| `backpressure` | Есть ограничение очереди/конкурентности вместо неограниченного буфера |
| `circuit-breaker-external` | У внешних зависимостей есть брейкер и таймаут |
| `partitioned-by-key` | Шардирование/партиционирование по осмысленному ключу |
| `observability-sampled` | Трейсы и логи семплируются, а не пишутся 1:1 |
| `graceful-degradation` | Есть путь деградации (stale-from-cache) при отказе зависимости |
| `ryw-where-it-matters` | Там, где пользователь читает собственную запись, включено средство read-your-writes |
| `idempotency-on-at-least-once` | У всех консьюмеров at-least-once есть ключ идемпотентности |
| `conflict-strategy-declared` | В `active-active` явно выбрана стратегия разрешения конфликтов, отличная от молчаливого LWW |
| `multi-az-and-region` | Критический путь пережил и `az-failure`, и `region-failure` |
| `dns-ttl-matches-rto` | TTL DNS согласован с целевым RTO (а не 3600 с при RTO = 60 с) |
| `residency-respected` | Данные пользователей не покидают требуемый регион |

| `sync-call-to-slow-op` | 12 | Синхронный вызов операции с p99 > 1 с |

| `no-timeout` | 10 | Ребро без таймаута |
| `retry-without-budget` | 10 | Ретраи без бюджета/брейкера — риск лавины |
| `unbounded-queue` | 8 | Очередь без ограничения и без алерта на лаг |
| `cache-no-ttl-no-eviction` | 8 | Кэш без TTL и без политики вытеснения |
| `rf1-on-durable-data` | 12 | Долговечные данные с RF = 1 |
| `chatty-fanout` | 8 | Sync-веер > 10 вызовов (хвост убьёт p99) |
| `deep-sync-chain` | 8 | Синхронная цепочка глубже 5 хопов |
| `write-through-no-persistence` | 8 | Кэш как источник истины без персистентности |
| `hot-partition` | 10 | Ключ шардирования даёт > 30% трафика на одну партицию |
| `n-plus-one` | 6 | `fanout` к БД > 20 на один входящий запрос |
| `orphan-node` | 3 | Блок без трафика |
| `log-everything` | 6 | Логи дороже, чем compute, и без семплирования |
| `over-provisioned` | 5 | Все узлы ρ < 0.1 при пике — переплата |
| `silent-lww` | 14 | `active-active` с `lww` без явного обоснования: записи теряются молча |
| `rmw-without-cas` | 12 | Read-modify-write на конкурентном ключе без CAS и блокировок |

| `at-least-once-not-idempotent` | 12 | Ретраи и at-least-once без ключа идемпотентности |
| `cross-region-sync-write` | 8 | Синхронная запись через межрегиональный линк на горячем пути — `+RTT` в p99 каждой записи |
| `dns-ttl-vs-rto` | 8 | TTL DNS больше целевого RTO — переключение регионов физически не успеет |
| `region-without-capacity` | 10 | При отказе одного региона оставшиеся не вмещают его трафик |
| `residency-violation` | 15 | Данные с требованием резидентности приходят на хранение в другую юрисдикцию: межрегиональная репликация или запись наружу (чтение из чужого региона и репликация внутри той же юрисдикции нарушением не считаются) |

Каждое правило в UI: симптом → почему плохо → что попробовать → «показать на схеме».
В режиме задания подсказка «что попробовать» скрыта до первой неудачной сдачи.

## 8. Эталонные решения и дифф

После сдачи (или после 3 неудачных попыток) открываются **2–3 эталонных решения** — принципиально
разных, а не «правильное и неправильное»:

Для «YouTube»:
* **A. Классика:** CDN + S3 + очередь транскодинга + Postgres (метаданные) + Redis + ClickHouse (аналитика).
* **B. Экономный:** собственные edge-кэш-серверы вместо коммерческого CDN, MinIO вместо S3 —
  дешевле в 3 раза, но сложнее в эксплуатации и хуже географическое покрытие.
* **C. Предельно масштабируемый:** Cassandra для метаданных, мультирегион, транскодинг на GPU —
  дороже, но держит ×10 роста без перепроектирования.

Дифф с решением пользователя показывается в двух видах:
1. **Метрический дифф** — таблица «ваше / A / B / C» по p99, $, доступности, простоте.
2. **Структурный дифф** — какие блоки есть у эталона и нет у вас (и наоборот), с однострочным
   объяснением роли каждого.

Эталон открывается двумя путями: кнопкой в панели задания после сдачи и в любой момент из
комбобокса «Примеры схем» в шапке — там демо-схемы и все 46 эталонов, сгруппированные по заданию
(`src/data/sampleSchemes.ts`). Второй путь ведёт в песочницу и не считается сдачей: он для того,
чтобы разобрать чужое решение, а не подсмотреть своё.

Каждый узел эталона подписан своей ролью — «Горячие ссылки», а не «Redis». Роли лежат в
`locales/{ru,en}/nodes.json` и ключуются идентификатором узла, поэтому одна и та же схема
читается на обоих языках, а `label` остаётся за пользователем (ADR-14). Новый узел в поставляемой
схеме без записи в словаре роняет `tests/components/nodeNames.test.ts`.

### Специальные наборы

Сделаны в фазе 4. Все три набора — не отдельный движок, а **производные задания**: `Challenge`
собирается из базового задания каталога функциями `src/engine/practice/derive.ts`, а дальше работает
тот же конвейер приёмки. Поэтому набор нельзя «сдать» иначе, чем обычное задание: те же предикаты,
тот же Realism Gate, та же батарея сценариев.

* **«Интервью»** — 6 сессий на 45–60 минут. Требования подкидываются этапами: на 0-й минуте базовые,
  на 20-й нагрузка вырастает в 3–10 раз и пересматривается бюджет, на 35-й приходит география или
  надёжность. Схему кандидат собирает с нуля — стартовая схема сессии равна стартовой схеме базового
  задания (один блок-клиент). Требования этапов **накапливаются**, а требование с тем же
  идентификатором **замещает** прежнее: так «бюджет ×10» выглядит пересмотром старого требования, а
  не вторым бюджетом. Масштабирование правит и стартовую схему, и `lockedParams`, и живую схему на
  холсте — Realism Gate после этого сходится. Подсказок и эталонных решений у сессии нет.
* **«Инцидент»** — 10 сломанных схем на 10 минут. Схема берётся из эталонного решения базового
  задания, к ней применяются правки `SchemePatch` (параметр, снятый узел, снятая связь, политика
  ребра, вид ребра). Инвариант набора закреплён тестом: **чистый эталон приёмку проходит, сломанный
  — нет**, причём падает он на hard gates или на сценариях, а не на Realism Gate: гейт называет
  параметр по имени и превратил бы задачу в подсказку. Причина поломки показывается только после
  того, как игрок сдал схему.
* **«Гольф»** — 5 задач на минимальную стоимость. Схема тоже берётся из эталона, но правки не ломают
  её, а **раздувают**: инстансы, шарды, реплики, брокеры выставляются заведомо выше нужного.
  Требование `budget` из задания снимается — счёт за месяц и есть результат. Цель (`par`) равна
  стоимости исходного эталона, поэтому золото достижимо по построению: достаточно вернуть раздутое
  обратно. Медали — золото до цели, серебро до цели ×1.3, бронза до ×1.7; медаль не считается, пока
  схема не прошла приёмку.

Прогресс наборов лежит отдельно от прогресса каталога, в `sd-practice`: число попыток, признак
решённости, лучшее время (для наборов с таймером) и лучший счёт (для гольфа). Таймер идёт в UI, а не
в движке: ядро остаётся чистым и детерминированным.

## 10. Полностью разобранный пример: «Видеохостинг»

### 10.1. Исходные данные и что из них следует

| Величина | Расчёт | Результат |
|---|---|---|
| Просмотров в сутки | 100 млн DAU × 5 | 500 млн |
| Средний RPS просмотров | 500e6 / 86 400 | **≈ 5 800 rps** |
| Пиковый RPS | ×3 | **≈ 17 400 rps** |
| Трафик на один просмотр | 6 мин × 4.5 Мбит/с / 8 | **≈ 202 МБ** |
| Egress в сутки | 500e6 × 202 МБ | **≈ 101 ПБ/сут** |
| Средняя полоса | 101 ПБ/сут | **≈ 9.4 Тбит/с** (пик ≈ 28 Тбит/с) |
| Хранение на видео (source + 5 качеств) | 1.5 ГБ + ≈ 0.67 ГБ | **≈ 2.2 ГБ** |
| Прирост хранилища | 50 000 × 2.2 ГБ | **≈ 110 ТБ/сут ≈ 40 ПБ/год** |
| За 3 года (с RF=1.5 через erasure coding) | 120 ПБ × 1.5 | **≈ 180 ПБ** |
| Транскодинг | 50 000 × 10 мин × 5 качеств / speedFactor 1.0 | **≈ 2 500 000 CPU-мин/сут ≈ 1 736 ядер непрерывно** |
| Метаданные | 50 000 × 3 года × 2 КБ | ≈ 110 ГБ — **тривиально**, это ловушка задания |

Ключевой урок задания: **узкое место здесь не БД и не сервисы, а egress и хранение.**
Стоимость раздачи 101 ПБ/сут напрямую из S3 по $0.09/ГБ ≈ **$273 млн/мес** — гарантированный
провал по бюджету. С CDN при hit ratio 0.95 и $0.02/ГБ — ≈ **$61 млн/мес** плюс наполнение кэша из
origin: 5% промахов по $0.09/ГБ — это ещё ≈ **$14 млн/мес**, и каждый процент промахов виден в
счёте (`docs/02-simulation.md` §9).
Дальше кандидат вынужден думать про долгосрочные контракты, собственные PoP и популярность контента
(Zipf: 5% видео дают 80% просмотров → маленький кэш даёт огромный эффект).

* **Задания каталога пишутся не в YAML, а в TypeScript-модулях** (`Challenge`-объект). Причина та же,
  что у блоков: типизация ловит опечатку на компиляции. Форма DSL совпадает с §2 один в один.
  Авторский YAML появился в фазе 4 как отдельный вход для пользовательских заданий (§12) — каталог
  на него не переезжает.
* **Поток задания = блок-клиент стартовой схемы** с тем же `id`. Это следствие решения фазы 1
  «каждый клиент — один поток»; параметры клиента заперты через `lockedParams`, их правка роняет
  Realism Gate.
* **`consistency` выражен через наблюдаемые аномалии**, а не через объявленный уровень:
  `strong` требует нулевой частоты `stale-read`, `read-your-writes`, `lost-update` и `lost-write-lww`.
* **Порядок конвейера** — сначала компиляция, потом Realism Gate: гейт читает поток и путь по графу,
  а их даёт только скомпилированная топология. Вердикт различает обе стадии.
* **Выделенная ёмкость хранилища** берётся из таблицы `PROVISIONED_STORAGE_GB` в `predicates.ts`
  (8 типов блоков): `StorageResult` фазы 1 знает объём данных, но не объявленную ёмкость.
* Ось «Бонусные цели» питается полем `bonusObjectives` — это обычные требования, которые не гейтят.

### 11.3. Не реализовано

* `custom`-предикат (§3, четырнадцатый вид) — произвольная функция не сериализуется в задание.
  Постановка внутренне противоречива, и это надо решить до реализации, а не в процессе: для
  заданий из репозитория `custom` не нужен (задания и так TypeScript-модули по решению D3, а
  `starter` и `build` эталона — уже функции, и тринадцати видов хватает на все 21). Нужен он ровно
  там, где функцией быть не может — в авторском режиме и импорте задания по ссылке (FR-CHL-9/10),
  то есть на недоверенном вводе в статическом приложении без `eval`. Это не «дописать предикат»,
  а спроектировать ограниченный язык выражений, грамматики которого нет ни в одном документе.
* **Структурный** дифф с эталоном (§8) — разница множеств блоков с ролью каждого. Метрический дифф
  реализован (пять осей: p99 худшего потока, стоимость, доступность, число блоков, пиковая
  загрузка), структурный требует сопоставления узлов, а идентификаторы у схемы игрока и у эталона
  независимы: функции соответствия нет.

  У метрического диффа есть правило, без которого он врал бы в самом частом случае: победой
  считается только сравнение схемы, которая **делает то, что требует задание** — все требования
  вида `capability` выполнены и схема несёт трафик. Иначе каждая ячейка помечается
  `incomparable`. Причина простая: пустая стартовая схема выигрывала все десять ячеек из десяти
  по всем заданиям — она дешевле, быстрее и доступнее любого эталона ровно потому, что не делает
  ничего. Равенство остаётся равенством и без этого условия: если дельта нулевая, это факт, а не
  заявка на превосходство, — благодаря чему эталон, сравнённый сам с собой, по-прежнему даёт
  нули. Побочный эффект правила приятный: эталоны-антипаттерны (`postgis-everything`,
  `origin-only-delivery` и ещё девять) сами оказываются несопоставимыми — у них не выполнены
  `capability`-требования, и «зато дешевле» про них больше не пишется.
* **Лидерборды** (FR-CHL-11) и **импорт задания по ссылке** (FR-CHL-10) — им нужен бэкенд или
  доверенный источник, а приложение статическое. Гольф считает личный лучший счёт локально.
* `slo`-метрика `completion.p95` для длинных операций (§10.2, R8): transient-режим в модели
  появился в фазе 3, но приёмка его не читает — предикаты смотрят только стационарный срез,
  ряд `timeline` в вердикт не входит.

### 11.4. Ограничения, найденные при написании каталога

Каталог из 23 заданий оказался лучшим тестом движка, чем модульные тесты: ниже — расхождения
модели с документом, которые он вскрыл. Они не мешают приёмке, но задают повестку следующей фазы.
Два пункта закрыты вместе с transient-режимом: `region-failure` теперь перекладывает трафик
отказавшего региона на живые, а кэш поглощает только чтения (`docs/02-simulation.md` §15.2).
Семь пунктов закрыты правкой самой модели: `fanout` и балансировка в свёртке задержек (§7),
атрибуция egress (§9), связь насыщения с ожиданием (§5.1–5.2), цена синхронной репликации
(§7а.3), дефолты `dlq` и разведение `geo.residency` с антипаттерном `residency-violation`.

| Что | Следствие для заданий |
|---|---|
| Realism Gate проверяет только `realistic`-диапазон, но не `min`/`max` схемы | Значение вне ползунка UI проходит гейт |
| `evaluateAnomaly` берёт первую аномалию с нужным кодом, а не максимум по узлам | При двух одинаковых хранилищах требование проверяется по первому |
| `buildScheme` не задаёт `EdgePolicy` | В эталонах недостижимы правила `idempotent-writes` и `graceful-degradation` |
| Ожидание downstream не входит в `serviceSec` вызывающего | Перегрузка внизу стека не поднимает утилизацию вверх по стеку: предикат `capacity` ловит только сам перегруженный узел |
| `REPLICATION_FACTOR` в `predicates.ts` знает 11 типов из 109: нет `aurora`, `vitess`, `cockroach`, `scylla`, `neo4j`, `timescale` | Требование `durability` на схеме с блоками волны V1 не выполнимо — вместо него в новых заданиях стоит `redundancy` |
| `PROVISIONED_STORAGE_GB` знает 10 типов: нет ни одного блока волны V1 | Требование `storage` выполнимо только если в схеме есть `s3`/`minio`/`clickhouse`/`postgres`; при этом объявленная ёмкость ничего не стоит |
| `redundancyOfNode` не знает избыточности у `audit-log`, `traces`, `influx`, `block`, `redis-streams`, `batch`, `trino`, `local-cache` | Любой такой блок с трафиком — SPOF: −15 линтера, и обойти это параметрами нельзя |
| `serviceSec` у `glacier` равно времени извлечения независимо от доли чтений | Любой синхронный вызов холодного архива даёт `sync-call-to-slow-op`, даже если из архива только пишут |
| `regionSpareRps` берёт минимум по всем узлам региона, включая те, что видят проценты трафика | Чтобы пройти `region-without-capacity`, запас нужен даже узлу, который обслуживает 2% запросов |
| `rate-limit-at-edge` ищет только `rateLimitRpsPerClient` | Правило выполнимо исключительно через `api-gateway`, хотя `waf` и `rate-limiter` тоже ограничивают частоту |
| `cacheHitRatio`, `compressionRatio` выше дефолта считаются «подкруткой» и штрафуются | Эталон, честно поднявший hit ratio, теряет 5 баллов за каждый такой параметр |

## 12. Конструктор заданий (FR-CHL-9)

Фаза 4. Своё задание пишется прямо в приложении — вкладка «Свои задания» в панели заданий,
кнопка «Новое задание». Формат тот же, что описан в §2 и §3: те же поля, те же тринадцать видов
требований. Отличий от заданий каталога ровно два, и оба следуют из того, что вход недоверенный.

**Стартовая схема — данные, а не функция.** В `Challenge` поля `starter` и
`referenceSolutions[].build` — функции, собирающие `SchemeV1`. В авторском задании вместо них
описывается сама схема, списками `nodes` и `links`, ровно как её принимает `buildScheme`:

```yaml
starter:
  nodes:
    - { id: users, type: client-web, params: { dau: 2000000, peakFactor: 3 } }
    - { id: edge, type: cdn }
  links:
    - { from: users, to: edge }
```

Кнопка «Схема с холста» дописывает такой блок из текущей схемы: параметры выгружаются только те,
что отличаются от умолчаний блока, — иначе фрагмент был бы нечитаемым.

**`custom`-предиката нет.** Четырнадцатый вид требования (§3) остаётся нереализованным именно здесь:
произвольная функция не сериализуется, а исполнять выражение из недоверенного текста в статическом
приложении без `eval` — значит спроектировать язык выражений, грамматики которого нет ни в одном
документе. Тринадцати видов хватило на все 23 задания каталога.

### 12.1. Поддерживаемое подмножество YAML

Парсер свой (`src/engine/authoring/yaml.ts`), около 300 строк, без зависимостей — тянуть в бандл
полноценный YAML ради авторского режима не стали. Поддерживаются:

| Что | Пример |
|---|---|
| Наборы полей с отступами | `title:` → `  ru: Моё задание` |
| Списки, в том числе с наборами внутри | `- id: R1` + следующая строка `  kind: slo` |
| Потоковые списки и наборы, вложенные | `tags: [cache, cost]`, `desc: { ru: …, en: … }` |
| Числа с подчёркиваниями, дроби, экспонента | `1_000_000`, `0.25`, `1e3` |
| Логические значения и пустота | `true`/`false`/`yes`/`no`, `null`, `~`, пустое значение |
| Строки в кавычках, одинарных и двойных | `'да: нет'`, `"перенос\nстроки"` |
| Блочные скаляры `\|` и `>` с отсечением `-` | многострочный `brief` |
| Комментарии и разделитель документа | `# текст`, `---` |
| JSON целиком | текст, начинающийся с `{`, разбирается как JSON |

Не поддерживаются: якоря `&`, ссылки `*`, теги `!`, сохраняющее отсечение `\|+`, несколько
документов в файле, отступ табуляцией. На каждый такой случай парсер возвращает код ошибки и номер
строки, а не падает. Одно осознанное отклонение от спецификации: хвостовые переводы строк у блочных
скаляров всегда срезаются, поэтому `brief` не тащит за собой пустую строку.

### 12.2. Проверка

Разобранный текст проходит `validateSpec` — она возвращает **список** проблем с путём до поля, а не
первую попавшуюся. Проверяются: типы блоков и группы (по реестру), совпадение потока с блоком
стартовой схемы, обязательные поля каждого вида требования, пороги у `slo`, `anomaly` и `geo`,
известность сценариев, уникальность идентификаторов, диапазоны чисел. Отдельным шагом схема
**собирается** через `buildScheme` — так несовместимость портов ловится в редакторе, а не на холсте.

Задания лежат в `localStorage` под ключом `sd-authored` вместе с исходным текстом: правка открывает
тот же текст, а не восстановленный из структуры. Запускается авторское задание тем же движком —
ссылка `{ kind: 'authored', spec }` уходит в воркер приёмки наравне со ссылками на каталог и наборы.
