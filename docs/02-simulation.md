# 02. Модель симуляции

Приложение к [PRD.md](../PRD.md). Описывает, как схема превращается в числа.

Принцип: **всё, что показывает симулятор, должно быть объяснимо одной формулой с подставленными
значениями.** Никаких «чёрных ящиков» — иначе тренажёр не учит, а гадает.

---

## 1. Общая схема расчёта

```
Scheme + Flows + Scenario
        │
        ▼
[1] TopologyCompiler ──► валидация, SCC, порядок обхода, дерево вызовов на каждый Flow
        │
        ▼
[2] Flow Solver (итерации до сходимости) ──► λ по узлам и рёбрам (read/write, по Flow)
        │            ▲
        │            └── обратная связь: ретраи и деградация меняют λ
        ▼
[3] Capacity Kernel ──► capacity, boundBy, ρ по каждому узлу
        │
        ▼
[4] Queueing ──► W_q, queueDepth, errorRate, throughput
        │
        ▼
[5] Monte-Carlo Latency Roll-up ──► p50/p95/p99 на каждый Flow, водопад по хопам
        │
        ▼
[5а] ConsistencyModel ──► частота аномалий по типам (режим по умолчанию — включён)
        │
        ▼
[6] Derived: storage / memory / logs / egress / cost / availability / RPO / RTO
        │
        ▼
[7] RuleEngine ──► Findings (bottleneck, SPOF, antipattern, SLO violation, anomaly)
```

Шаги 2–4 повторяются до сходимости (демпфированные итерации), потому что ретраи и сброс нагрузки
меняют входной поток. Шаги 5–7 выполняются один раз по сошедшемуся состоянию.

**Стоимость расчёта:** шаги 1–4 — O(V+E) на итерацию, ≤ 50 итераций. Шаг 5 — N сэмплов × глубина
дерева вызовов (N = 20 000 по умолчанию, 4 000 в режиме live-preview).

## 2. Шаг 1. Компиляция топологии

Аналог `GraphCompiler` в dsp-flow, но с принципиальным отличием: **циклы легальны**.

| Проверка | Действие |
|---|---|
| Совместимость портов и протоколов | Ошибка: «Клиент не может напрямую говорить по протоколу `sql` с Postgres» (настраиваемо) |
| Висящие рёбра, дубликаты | Ошибка |
| Компоненты связности (union-find) | Предупреждение «3 несвязанные подсхемы» |
| Узлы без входящего трафика | Предупреждение «блок не используется» |
| Циклы | **Не ошибка.** Ищем SCC (Тарьян); внутри SCC решаем итеративно, между SCC — топологический порядок |
| Дерево вызовов на Flow | Обход от `entryNodeId` по sync-рёбрам; async-ребро обрывает дерево (см. §5.4) |
| Глубина синхронной цепочки | Предупреждение при depth > 5 |

Результат — `CompiledTopology`: порядок обхода, дерево вызовов на каждый Flow, карта смежности,
список SCC.

## 3. Шаг 2. Распространение потока (Flow Solver)

### 3.1. Базовое уравнение

Для ребра `e: i → j` и класса трафика `κ` (Flow × {read, write}):

```
λ_e,κ  =  λ_i,κ · share_e · fanout_e · (1 − absorb_i,e)
λ_j,κ  =  Σ_e∈in(j) λ_e,κ
```

| Член | Смысл | Кто задаёт |
|---|---|---|
| `share_e` | Доля трафика, уходящая в это ребро при ветвлении (сумма по группе = 1) | Балансировщик — поровну; сервис — вручную |
| `fanout_e` | Сколько вызовов downstream на один входящий запрос (может быть > 1: батч, fan-out на N шардов) | Параметр ребра |
| `absorb_i,e` | Доля, поглощённая узлом `i` (попадание в кэш, ответ из локального кэша, 304 Not Modified) | Производное (Zipf-модель кэша) |

Клиентские блоки инжектируют начальный λ по своим Flow.

### 3.2. Усиление ретраями (retry amplification)

```
λ_offered_j = λ_nominal_j · (1 + A_retry_j)
A_retry_j   = Σ_{k=1..R} min(p_fail_j, retryBudget)^k
```

Где `p_fail_j` — вероятность отказа/таймаута на узле `j`, которая сама зависит от `λ_offered_j`.
Отсюда — **петля обратной связи**: перегруженный сервис получает ещё больше нагрузки от ретраев.
Это моделирует **retry storm** — один из самых поучительных эффектов (и один из сценариев батареи).

Если у ребра `circuitBreaker = true`, то при `p_fail > порога` `A_retry → 0` и трафик обрывается на
источнике (`fail fast`) — сравнение схем с брейкером и без наглядно показывает его смысл.

### 3.3. Итерационный решатель

```
λ⁰ ← прямой проход в топологическом порядке (ретраи выключены)
повторять n = 1..50:
    пересчитать ρ, p_fail по λⁿ⁻¹
    λ_new ← прямой проход с учётом ретраев и absorb
    λⁿ ← (1 − ω)·λⁿ⁻¹ + ω·λ_new          # демпфирование, ω = 0.5
    если ‖λⁿ − λⁿ⁻¹‖∞ / ‖λⁿ‖∞ < 0.001 → выход
```

Расходимость (λ растёт неограниченно) — это **не баг, а результат**: «схема неустойчива, ретраи
образуют лавину». Симулятор в этом случае помечает Finding `retry-storm` и показывает точку срыва.

### 3.4. Гео-маршрутизация и мультирегион

Мультирегион входит в MVP (решение **D1**), поэтому распространение потока двухступенчатое:
сначала клиенты распределяются по регионам, затем внутри региона работает обычный решатель.

**Шаг 1 — распределение по географии.** Flow объявляет `clientGeo` — распределение по гео-зонам
(`na-east`, `na-west`, `eu-west`, `eu-central`, `apac-se`, `apac-ne`, `sa`, `me`, `africa`, `oceania`).
Блок `dns`/`glb` по своей `routingPolicy` отображает зону в регион:

```
λ_region,flow = λ_flow · Σ_zones share(zone) · route(zone → region)

route =  latency   → ближайший здоровый регион по матрице RTT
         geo       → явная карта зона→регион (data residency)
         weighted  → заданные веса
         failover  → primary, пока жив; иначе следующий по списку
```

**Шаг 2 — разделение по операциям.** В зависимости от `multi-region-policy.mode`:

| Режим | Чтения | Записи |
|---|---|---|
| `single` | все в единственный регион | туда же |
| `active-passive` | в активный регион | в активный регион |
| `active-active` | локально | локально (→ источник конфликтов) |
| `read-local-write-global` | локально | все в `writeRegion` (+ межрегиональный RTT к latency записи) |
| `sharded-by-geo` | локально по «домашнему» региону ключа | туда же; «чужие» ключи — с межрегиональным хопом |

**Шаг 3 — трафик репликации.** Порождается автоматически, а не рисуется руками:

```
λ_repl = λ_write,region · (числоРегионов − 1) · directionFactor
байт/с = λ_repl · recordBytes · (1 + overhead)
стоимость = байт/мес · costPerGb(link-cross-region)
```

**Зеркальные регионы.** Регион с `mirrorOf` наследует все узлы, рёбра и параметры прототипа;
собственным у него остаётся только `trafficShare` и результаты симуляции. Это ключевое требование
удобства: без него нарисовать три региона вручную — заведомо неподъёмная работа, и мультирегион в
MVP не имел бы смысла.

**RPO и RTO** считаются здесь же:

```
RPO_actual = replicationLag.p99                       (сколько данных теряется при потере региона)
RTO_actual = detectionSec + dnsTtlSec + failoverSec + warmupSec
```

`dnsTtlSec` часто оказывается доминирующим слагаемым — и это один из самых полезных неочевидных
уроков тренажёра.

## 4. Шаг 3. Ядро ёмкости (Capacity Kernel)

Единая формула для всех блоков — только набор слагаемых различается:

```
capacity_i = min over resources r of  limit_r
```

| Ресурс `r` | Формула `limit_r` | Для кого характерен |
|---|---|---|
| Воркеры/CPU (закон Литтла) | `instances · concurrencyPerInstance / S` | Сервисы, воркеры |
| Явный потолок | `instances · maxRpsPerInstance` | API GW, LB, managed-сервисы |
| Соединения | `maxConnections · instances / connectionsPerRequest / S` | **Postgres, MySQL** |
| IOPS | `provisionedIops / iopsPerRequest` | Диски, RDS |
| Сеть | `networkMbps / (payloadBytes · 8 / 10⁶)` | CDN, файлы, реплики |
| Память | `memoryGb / memoryPerRequestGb` (для in-memory) | Кэши, векторные БД |
| Партиции | `partitions · maxRpsPerPartition` | Kafka, Kinesis, DynamoDB |
| Вендорский юнит | `rcu / rcuPerRead`, `wcu / wcuPerWrite` | DynamoDB |
| Кворум | `1 / quorumRoundTripSec` | etcd, ZooKeeper |
| Лицензия/квота | `quotaRps` | Внешние API |

Движок обязательно сохраняет `boundBy` — **имя ресурса, давшего минимум**. Это главный
дидактический артефакт: «упёрлись не в CPU, а в `maxConnections`».

```
ρ_i = λ_offered_i / capacity_i
```

**Автоскейлинг** (в steady-state): `instances = clamp(ceil(λ·S/(concurrency·targetUtil)), min, max)`.
В transient-режиме добавляется `scaleUpLagSec` — и видно, как во время всплеска сервис
захлёбывается, пока приезжают новые поды.

## 5. Шаг 4. Очереди и деградация

### 5.1. Время ожидания

Аппроксимация Сакасэгавы для M/M/c с поправкой Аллена–Каннина на вариативность (G/G/c):

```
W_q(M/M/c) = S · ρ^(√(2(c+1)) − 1) / (c · (1 − ρ))
W_q(G/G/c) = W_q(M/M/c) · (c_a² + c_s²) / 2
```

| Символ | Значение | Дефолт |
|---|---|---|
| `S` | Среднее время обслуживания | из параметров блока |
| `c` | Число обслуживающих приборов, см. ниже | |
| `c_a²` | Квадрат коэффициента вариации интервалов прихода | 1.0 (Пуассон); 2–4 при `burstiness`, 8+ при `thundering-herd` |
| `c_s²` | То же для времени обслуживания; для логнормального = `e^{σ²} − 1` | σ = 0.5 → 0.28; σ = 1.2 → 3.1 |

**Приборы считаются по связывающему ресурсу, а не по объявленному параллелизму:**

```
c = min(instances × concurrencyPerInstance, capacity · S)
```

Второе слагаемое — закон Литтла наоборот: сколько обслуживаний идёт параллельно, когда узел
работает на пределе ёмкости. Без этой поправки сервис с `concurrencyPerInstance = 200` на четырёх
ядрах считался бы M/M/800 и не показывал бы очереди даже на 95% загрузки, хотя реально держит
в обслуживании 107 запросов — и ожидание на подходе к ёмкости занижалось на порядок.

Полное время на узле: `T_i = S_i + W_q,i`. Длина очереди: `L_q = λ · W_q` (закон Литтла).

### 5.2. Сброс и таймауты

```
throughput_i = min(λ_offered_i, capacity_i)
p_overflow   = max(0, 1 − capacity_i / λ_offered_i)
p_timeout    = (1 − p_overflow) · exp(−timeout_i / (S_i + W_q,i))
p_fail_i     = 1 − (1 − p_overflow)(1 − p_timeout)
```

При `queueLimit = 0` (без очереди) избыток немедленно отбрасывается с 503 — «shed load».
При большой очереди latency улетает в небо, но ошибок нет: классический трейд-офф, который
симулятор показывает наглядно.

**Ожидание ограничено сливом полной очереди** — дольше, чем стоит вся очередь, ждать физически
нельзя:

```
W_drain        = queueLimit / capacity            (0, если очереди нет)
W_q            = min(W_q(G/G/c), W_drain)
queueFullShare = W_q / W_drain                    ← доля времени, что очередь стоит полной; при ρ ≥ 1 равна 1
```

`queueFullShare` уходит в свёртку задержек (§7): под перегрузкой очередь стоит полной, поэтому
ожидание перестаёт быть экспоненциальным и становится детерминированным временем слива. Именно
так насыщение попадает в p50 и p99, а не только в `errorRate`.

### 5.3. Каскад

`p_fail` узла превращается в ошибки у вызывающего, а те — в ретраи (§3.2) и в срабатывание
таймаутов вверх по стеку. Симулятор помечает **цепочку каскада** отдельным цветом: видно, как
падение одной БД валит пять сервисов.

### 5.4. Асинхронные рёбра

Async-ребро (`kind: 'async'`) **разрывает цепочку latency**: вызывающий не ждёт. Вместо этого
считается:

```
lagSeconds     = backlog / consumerThroughput
timeToDrain    = backlog / max(0, consumerThroughput − producerRps)
completionTime = enqueueLatency + lagSeconds + processingTime   ← «время до готовности результата»
```

Если `producerRps > consumerThroughput`, backlog растёт линейно; симулятор считает
`timeToRetentionOverflow = retentionBytes / (growthRate)` и выдаёт Finding «через 4.2 часа начнётся
потеря сообщений».

### 5.5. Transient-режим: ход времени

Стационарный расчёт отвечает на вопрос «выдержит ли схема такую нагрузку». Он не отвечает на
вопрос «что произойдёт в первые две минуты всплеска», потому что в стационаре автоскейлер уже
доехал, очередь уже пуста, а кэш уже прогрет. Transient-режим прогоняет схему **по шагам времени**:
на каждом шаге заново решается стационарная задача при текущем входном λ и текущем числе
инстансов, а между шагами эволюционируют величины с памятью.

Шаг длиной `Δ` считается в два прохода:

1. **проход спроса** — решатель (§3) с текущим числом инстансов возвращает `desiredInstances`
   каждого узла при нынешнем λ;
2. **лаг масштабирования** — фактическое число инстансов подтягивается к желаемому:
   `n ← n + (n_desired − n) · min(1, Δ / lag)`, где `lag = scaleUpLagSec` при росте и
   `scaleDownLagSec` при сжатии, плюс `schedulingLagSec` кластера, если узел лежит внутри
   `k8s-cluster`;
3. **проход состояния** — решатель повторяется с фактическим числом инстансов; его результат и
   становится точкой ряда.

Двухпроходность нужна, чтобы автоскейлер с нулевым лагом успевал среагировать внутри своего шага,
а не отставал на шаг из-за порядка вычислений.

Что эволюционирует между шагами:

| Величина | Как меняется |
|---|---|
| Инстансы | Первый порядок с лагом (формула выше); вниз медленнее, чем вверх |
| Очередь (backlog) | `pending = backlog + λ·Δ`, обслужено `min(pending, C·Δ)`, остаток ждёт: `backlog ← min(pending − served, L)` |
| Потерянные запросы | Всё, что не влезло в буфер: `dropped = pending − served − backlog`, `p_overflow = dropped / (λ·Δ)` |
| Прогрев кэша | `w ← w + (1 − w)·(1 − e^{−Δ/τ})`, `τ = M / λ_read` в пределах 20…900 с; hit ratio узла умножается на `w` |
| Ядовитые сообщения | `stuck ← stuck + share·λ·Δ − retire·Δ`; занятая ими доля ёмкости консьюмера — `stuck / (redelivery · C)`; при наличии `dlq` они уходят после `POISON_MAX_ATTEMPTS` попыток, без него копятся |

Размер буфера `L` зависит от узла: для синхронного это `queueLimit` (запросов), для узла за
async-ребром и для брокеров — `C · BUFFERED_BACKLOG_SEC`, то есть час ёмкости. Отсюда главное
свойство модели: **очередь не исчезает вместе с нагрузкой**. После спада она рассасывается со
скоростью `C − λ`, и время восстановления видно на ряде.

Задержка в точке ряда считается аналитически, без Monte-Carlo (иначе прогон стоил бы 60 свёрток):

```
p99 = S · e^{σ·2.3263} + min(W_q · ln(1/0.01), L/C) + backlog/C
```

— квантиль логнормального обслуживания, экспоненциальный хвост ожидания (ограниченный временем
полного слива очереди) и время разбора накопленного backlog.

Входное воздействие задаёт сценарий (§12): форма `λ(t)` — ступенька, рампа, плато или залп —
плюс окна, в которых узлы выключены (`db-failover`), замедлены (`slow-dependency`), потеряли часть
ёмкости из-за перекоса ключей (`hot-key`) или лишились бюджета ретраев (`retry-storm`).
Перекос считается через число шардов: `C_eff = C / (f·N + 1 − f)`, где `f` — доля трафика на
горячий ключ, `N` — число шардов. К λ добавляется детерминированный по seed джиттер
`exp(σ_j·ξ)`, `σ_j = 0.02 · c_a²` (не больше 0.12).

Результат прогона — ряд `timeline`: шаг, горизонт и по точке на шаг. В точке лежат вход λ,
пропускная способность, доля ошибок, пик утилизации, худший p99, суммарный backlog, суммарное
число инстансов, флаг нарушения SLO и разрез по всем узлам (λ, ёмкость, утилизация, инстансы
фактические и желаемые, очередь, ошибки, p99, hit ratio). Нарушением считается доля ошибок выше
1% или утилизация ≥ 1 хотя бы у одного узла; в сводке ряда есть момент первого нарушения и момент
восстановления.

Стационарный результат при этом никуда не девается: для transient-сценария он считается **в худшей
точке** воздействия (пик нагрузки, узел выключен, зависимость замедлена) — это и есть ответ на
вопрос «а если бы это состояние держалось вечно». Сценарий, которому не на чем сработать
(`db-failover` без хранилища, `slow-dependency` без внешней зависимости), ряда не даёт вовсе.

## 6. Кэш: hit ratio как производная величина

Ключевая обучающая механика: **hit ratio не задаётся, а вычисляется** из размера кэша и
распределения популярности.

Популярность ключей — Ципф с параметром α:

```
M = cacheMemoryBytes / (keyBytes + valueBytes + overheadBytes)      # сколько ключей влезло
h = H(M, α) / H(N, α),   где H(n, α) = Σ_{k=1..n} k^(−α)
```

Для α = 1 (типичный веб-трафик) при больших n: `H(n,1) ≈ ln n + 0.5772`, то есть

```
h ≈ (ln M + 0.577) / (ln N + 0.577)
```

| N (уникальных ключей) | M (влезло в кэш) | h |
|---|---|---|
| 10⁹ | 10⁶ | ≈ 0.67 |
| 10⁹ | 10⁷ | ≈ 0.78 |
| 10⁷ | 10⁶ | ≈ 0.86 |
| 10⁷ | 10⁴ | ≈ 0.58 |

Пресеты α: `0.6` — равномерный (плохо кэшируется), `1.0` — веб, `1.3` — соцсеть/новости,
`2.0` — сильно скошенный (звёзды, тренды).

**Поправки:**
* Инвалидация записью: `h_eff = h · (1 − writeShare · invalidationFactor)`.
* TTL: если `TTL < среднего интервала повторного обращения`, `h_eff` падает — считаем через
  вероятность повторного обращения внутри окна TTL.
* Холодный старт: `h(t) = h_∞ · (1 − e^{−t/τ})`, `τ ≈ M / λ_read` — используется в сценарии `cache-flush`.
* Hot key: доля трафика на топ-1 ключ = `1/H(N,α)`; если она превышает пропускную способность
  одного шарда — Finding `hot-key`, даже при отличном общем hit ratio.

Ручной override разрешён, но помечается бейджем «допущение пользователя» и учитывается в рубрике
заданий (нельзя «выиграть», выставив hit ratio = 0.999).

## 7. Шаг 5. Свёртка задержек: Monte-Carlo

Аналитически сложить p99 по хопам нельзя (p99 суммы ≠ сумма p99). Поэтому — прямое
семплирование по дереву вызовов, с фиксированным seed.

```
для каждого Flow f:
  для s = 1..N (N = 20 000):
     latency[s] ← walk(entryNode, f, rng)
  p50, p95, p99 ← квантили latency

walk(node, flow, rng):
  t ← sample_service_time(node, rng)          # LogNormal(median = S, σ)
  t ← t + sample_queue_wait(node, rng)        # W_q · (queueFullShare + (1 − queueFullShare) · Exp(1)), §5.2
  если replicationMode ∈ {sync, semi-sync} и rng.bernoulli(writeShare):
     t ← t + ackShare · RTT_до_самой_дальней_реплики        ← кворум ждёт реплику (§7а.3)
  если node из групп edge/clients:  ветви ← одно ребро, выбранное по weight   ← трафик делится
  иначе:                            ветви ← все sync-рёбра, каждое повторено fanout раз  ← веер
  для каждой ветви e:
     если e — кэш и rng.bernoulli(h) → пропустить (попадание, downstream не вызывается)
     t_e ← network_latency(e, rng) + walk(target(e), flow, rng)
     учесть ретраи: с вероятностью p_fail — повтор с задержкой backoff
  если node.callMode = sequential:  t ← t + Σ t_e
  если node.callMode = parallel:    t ← t + max(t_e)          ← tail amplification
  вернуть t
```

**Балансировка против веера — то же правило, что и в решателе (§15.2).** Плечи, между которыми
трафик делится по `weight` (узлы групп `edge` и `clients`), складывать нельзя: запрос уходит ровно
в одно из них, выбранное по весам. Плечи, которые вызываются все (веер), складываются в
`sequential` и дают максимум в `parallel`. Число вызовов на одно ребро — это `fanout` ребра:
целая часть разыгрывается как повторные вызовы, дробная — как Бернулли, поэтому `fanout = 0.5`
означает «downstream вызывается на каждом втором запросе», а `fanout = 10` стоит десяти вызовов и
в ёмкости, и в SLO.

**Что это даёт бесплатно:**
* Корректный «эффект хвоста при веере» (*tail at scale*): при 10 параллельных вызовах с p99 = 50 мс
  p99 всего запроса ≈ p99 максимума ≈ значительно хуже 50 мс. Один из самых недооценённых эффектов
  в system design — и он виден на графике сразу.
* Корректный вклад ретраев и таймаутов в хвост.
* Кэш-промахи как бимодальное распределение (виден «горб» на гистограмме).
* Цену синхронной репликации: запись ждёт подтверждения реплики, и это видно в p99 записи.

**Сетевые задержки** (`network_latency`) берутся из топологии: внутри AZ / между AZ / между
регионами / интернет — см. §11.

## 7а. Модель согласованности и аномалий

Управляется настройкой **«Модель согласованности»** (решение **D2**):

| Режим | Что делает | Стоимость расчёта |
|---|---|---|
| `выкл` | Согласованность игнорируется | 0 |
| `атрибут` | Уровень согласованности — просто объявленное свойство блока; проверяется предикатами заданий | ~0 |
| **`симуляция аномалий`** (по умолчанию) | Считается частота каждого типа аномалии в операциях в секунду и в процентах, с указанием источника | O(V+E), единицы миллисекунд |

Расчёт аналитический и дешёвый — поэтому режим включён по умолчанию без ущерба для отзывчивости.

### 7а.1. Базовое распределение лага

```
L ~ LogNormal(median = replicaLagMs, σ = replicaLagSigma)
P(L > t) = 1 − Φ( (ln t − ln median) / σ )
```

| Источник лага | median по умолчанию |
|---|---|
| Синхронная репликация | ≈ 0 (но `+RTT` к latency записи) |
| Полусинхронная | 5–20 мс |
| Асинхронная внутри AZ | 20–100 мс |
| Асинхронная между AZ | 50–300 мс |
| **Между регионами** | `RTT/2 + очередь` → 30–500 мс, при перегрузке — секунды |
| CDC/Kafka-конвейер | 200 мс – 5 с |

Лаг растёт с утилизацией источника: `median_eff = median · (1 + ρ_primary²/(1−ρ_primary))` —
перегруженный primary реплицируется хуже, и это видно.

### 7а.2. Типы аномалий и формулы

**A1. Устаревшее чтение (stale read)**
```
rate_A1 = λ_read · replicaShare · E_Δt[ P(L > Δt) ]
```
При кворуме `R + W > N` → `rate_A1 ≈ 0` (в отсутствие отказов узлов).
`replicaShare` берётся из `readRouting` ребра.

**A2. Нарушение read-your-writes**
```
rate_A2 = λ_read · readAfterWriteShare · replicaShare · P(L > Δt_raw)
```
Подмножество A1, но самое болезненное для пользователя: «я отправил комментарий и не вижу его».
`Δt_raw` — распределение задержки между записью и последующим чтением из параметров Flow.

**A3. Нарушение монотонности чтений**
```
rate_A3 = rate_A1 · (1 − stickyReadShare) · (1 − 1/nReplicas) · P(|L₁ − L₂| > Δt_между_чтениями)

          где |L₁ − L₂| ≈ LogNormal(median, σ√2) — разность двух независимых лагов
```
Наблюдаемый эффект — «значение поехало назад во времени».

Формула строится **поверх ставки A1**, а не рядом с ней, и это принципиально. Нарушение
монотонности — частный случай устаревшего чтения: чтобы заметить, что время пошло назад, надо
сначала прочитать свежее значение, а потом более старое. Три множителя добавляют к A1 ровно
недостающие условия: чтение не закреплено за одной репликой (`1 − stickyReadShare`), два чтения
попали на **разные** реплики (`1 − 1/nReplicas`), и реплики разъехались сильнее, чем интервал
между чтениями.

> Ранняя редакция этого раздела задавала A3 как `λ_read · (1 − stickyShare) · … · P(|L₁ − L₂| > Δt)`
> — без единого члена, описывающего запись. Такая формула считает вероятность того, что реплики
> *разъехались*, а не того, что это *можно заметить*: на узле, где по ключу почти не пишут, она
> объявляла аномальными до 80% чтений при доле устаревших чтений 0.002%. Подмножество не может
> быть больше множества, поэтому формула исправлена, а не только реализация.

**A4. Потерянное обновление (lost update)**
```
λ_key       = λ_write / effectiveKeys            (для горячего ключа — из Ципфа, см. §6)
P_collision = 1 − e^(−λ_key · W_rmw)             (W_rmw — окно read-modify-write)
rate_A4     = λ_write · P_collision · lostFactor
```

| `concurrencyControl` | `lostFactor` | Побочный эффект |
|---|---|---|
| `none` | 1.0 | Данные теряются молча |
| `optimistic` (CAS/версии) | 0 | Коллизия превращается в ретрай: `+λ_retry`, рост latency при контенции |
| `pessimistic` (блокировки) | 0 | Коллизия превращается в ожидание блокировки: **сериализация на ключе**, которая возвращается в §4 как отдельный ограничитель ёмкости `key-lock` |
| `crdt` | 0 | Слияние без потерь, но растут метаданные |

**A5. Конфликт записи в мульти-мастере** (только `mode: active-active`, `bidirectional`)
```
T_prop      = межрегиональный лаг репликации
P_conflict  = 1 − e^(−(Σ_другие_регионы λ_key,region) · T_prop)
rate_A5     = λ_write · P_conflict
lostWrites  = rate_A5 · (conflictResolution == 'lww' ? 0.5 : 0)
```
**Last-write-wins молча теряет примерно половину конфликтующих записей** — центральный урок
заданий уровня 5. `crdt` и `single-writer-per-key` дают 0 потерь, но платят своей ценой.

**A6. Дубликат обработки**
```
rate_A6 = λ_async · [deliverySemantics == 'at-least-once'] · redeliveryRate · (1 − idempotencyKey)
redeliveryRate ≈ p_fail_consumer + rebalanceRate + visibilityTimeoutExpiry
```

**A7. Нарушение порядка**
```
rate_A7 = λ_async · [гарантия порядка отсутствует] · (1 − e^(−λ_async,key · W_processing)) · (1 − 1/lanes)

          lanes = min(partitions, consumers)     — сколько независимых дорожек у одного ключа
```
Гарантия порядка нормализуется из разнородных параметров брокеров: `orderingScope` у Kafka
(`per-key`, `per-partition`, `global` считаются упорядоченными), `queueType: fifo` у SQS. **Брокер,
у которого параметра порядка нет вообще** — RabbitMQ, NATS, Kinesis, Redis Streams, SNS —
считается неупорядоченным: между несколькими консьюмерами они порядок и не гарантируют.
Число консьюмеров берётся из `consumersPerGroup` брокера, если он есть, иначе из
`instances × concurrency` узла-потребителя.

**A8. Аномалии изоляции SQL** (грязное, неповторяющееся, фантомное чтение)
```
rate_A8 ≤ λ_read · (1 − e^(−λ_write,key · W_tx))     W_tx = serviceSec · 2
```
Множество возможных аномалий задаётся таблицей соответствия, частота — вероятностью того, что
конкурирующая транзакция затронула тот же ключ внутри окна транзакции:

| `isolationLevel` | Грязное чтение | Неповторяющееся чтение | Фантомное чтение |
|---|---|---|---|
| `read-uncommitted` | да | да | да |
| `read-committed` | — | да | да |
| `repeatable-read` | — | — | да |
| `snapshot` | — | — | — |
| `serializable` | — | — | — |

Все три кода помечены признаком `upperBound` и выводятся со знаком `≤`: различать их частоты
по отдельности значило бы выдумать точность, которой в модели нет.

### 7а.3. Средства смягчения и их цена

Каждое средство не просто «выключает» аномалию, а переносит стоимость в другое место модели —
именно этот перенос и есть предмет обучения.

| Средство | Убирает | Чем платим (считается движком) |
|---|---|---|
| `sticky-primary` после записи | A2, A3 | Рост нагрузки на primary; в мультирегионе — `+RTT` до `writeRegion` |
| `version-token` (RYW-токен) | A2 | Иногда ожидание догона реплики; сложность клиента |
| `wait-for-lag` | A1, A2 | `+E[L]` к latency чтения — прямо в p99 |
| Кворум `R + W > N` | A1 | `+latency` (ждём R ответов), падение доступности при отказах |
| Синхронная репликация | A1, A2, RPO = 0 | **`+RTT` к каждой записи** (считается, см. ниже), падение write-throughput (не считается) |
| `optimistic` / CAS | A4 | Ретраи и рост latency при контенции |
| `pessimistic` блокировки | A4 | Сериализация на ключе → новый ограничитель ёмкости |
| `crdt` | A4, A5 | Ограничения на типы данных, рост объёма метаданных |
| `single-writer-per-key` | A5 | `+RTT` для «чужих» ключей |
| `idempotencyKey` | A6 | Хранение ключей идемпотентности + их TTL и объём |
| Ключ партиционирования | A7 | Ограничение параллелизма консьюмеров |

**Цена подтверждения репликации.** `replicationMode` хранилища добавляет к каждой записи ожидание
подтверждения реплик — иначе `sync` бесплатно обнулял бы устаревшие чтения, read-your-writes и RPO:

```
ackSec = ackShare · RTT_реплики
ackShare      = 1 для sync (ждём самую медленную реплику), 0.5 для semi-sync (ждём самую быструю)
RTT_реплики   = networkMs самого дальнего нарисованного ребра репликации,
                иначе RTT между AZ (0.35–1.2 мс), если у блока объявлены реплики
```

В Monte-Carlo надбавка разыгрывается по Бернулли с вероятностью `writeShare` узла, поэтому попадает
только в записи. Межрегиональная синхронная репликация стоит полного RTT (для Европа ↔ Америка это
80 мс на запись) — ровно та цена, которую в реальности платят за RPO = 0.

### 7а.4. Что видит пользователь

```
Согласованность · поток «checkout»
  Устаревшие чтения           2 340 op/s   0.42% чтений   ← Postgres replica (лаг p99 180 мс)
  из них read-your-writes     2 080 op/s   0.37%          ← самое заметное для пользователя
  Потерянные обновления          12 op/s   0.9% записей   ← нет CAS на строке `balance`
  Конфликты мульти-мастера        4 op/s   0.3% записей   ← LWW теряет ≈ 2 записи/с
  Дубликаты обработки             0 op/s                  ← ключ идемпотентности включён ✓
```

## 8. Шаг 6. Хранилище, память, логи

### 8.1. Полезные данные

```
growthGbDay = λ_write · 86400 · recordBytes · (1 + indexOverhead) · RF / compressionRatio / 10⁹
totalGb(t)  = initialGb + growthGbDay · t          (с учётом retention: t = min(t, retentionDays))
```

Дефолты: `indexOverhead` 0.2–1.0 (зависит от числа индексов), `RF` 1 (одна нода) / 3 (Cassandra,
HDFS) / 2–6 (реплики SQL), `compressionRatio` 1 (SQL по умолчанию) / 5–15 (ClickHouse, Parquet).

### 8.2. Медиа и блобы

```
storageGbDay = uploadsPerDay · (sourceSizeGb + Σ renditions_i.bitrateMbps · durationSec / 8 / 1000)
egressGbDay  = viewsPerDay · watchedSec · bitrateMbps / 8 / 1000
```

### 8.3. Логи, метрики, трейсы

```
logsGbDay    = Σ_services λ_i · linesPerRequest_i · bytesPerLine_i · 86400 · samplingRate / 10⁹
metricsGbDay = activeSeries · (86400 / scrapeIntervalSec) · bytesPerSample / 10⁹
tracesGbDay  = Σ λ_i · traceSampling · spansPerRequest · spanBytes · 86400 / 10⁹
```

`spansPerRequest` берётся из глубины дерева вызовов автоматически — то есть усложнение
архитектуры автоматически удорожает наблюдаемость. Полезный урок.

### 8.4. Память

```
cacheMemoryNeededGb = uniqueActiveKeys · (keyBytes + valueBytes + overheadBytes) / 10⁹
dbWorkingSetGb      = hotRowsFraction · rowCount · rowBytes / 10⁹
wsConnectionsMemGb  = concurrentConnections · memoryPerConnKb / 10⁶
```

### 8.5. Бэкапы

```
backupGbMonth = totalGb · (fullsPerMonth + incrementalRatio · incrementalsPerMonth) · retentionMonths
```

## 9. Шаг 6б. Стоимость

```
costMonth_i = compute + storage + egress + requests + managedPremium
   compute  = instances · costPerInstanceHour · 730
   storage  = totalGb · costPerGbMonth  (+ IOPS-плата для io2/provisioned)
   egress   = egressGbMonth · costPerGbEgress
   requests = (λ · 2.63·10⁶ / 10⁶) · costPerMillionRequests      # 2.63e6 сек в месяце
   managed  = коэффициент 1.0–2.5× к self-hosted
```

Профили цен (`pricingProfile`): `aws`, `gcp`, `azure`, `hetzner`, `on-prem`, `custom`.
Каждый профиль — версионированный JSON с датой актуальности; в UI показывается плашка
«цены на 2026-Q2, могут устареть».

**Egress платится там, где трафик реально покидает периметр** — иначе экономика CDN держалась бы
на бесплатном наполнении кэша. Три правила атрибуции:

| Что за трафик | Кто платит | За что |
|---|---|---|
| Ребро от клиента (`scope = internet`) | тот, кто отвечает клиенту | `responseBytes` ответа |
| Ребро от CDN к origin (PoP стоят вне периметра) | origin | `responseBytes` наполнения кэша |
| Вызов внешнего сервиса (`external-api`) | вызывающий | `requestBytes` запроса |

Трафик между AZ и между регионами оплачивается отдельно, по ставкам `crossAzPerGb` и
`crossRegionPerGb` профиля цен.

**Egress — главный источник «вау»:** прямая раздача видео из S3 при $0.09/ГБ против CDN c
$0.02/ГБ и кэш-хитом 95% (то есть 5% ходят в origin и оплачиваются как egress origin) даёт
$0.09 против $0.02 + 0.05·$0.09 = $0.0245 за гигабайт — разница в 3.7×. Кэш-хит здесь виден в счёте
напрямую: каждый процент промахов добавляет к счёту 1% трафика по цене origin, поэтому CDN с
хитом 0.92 вместо 0.98 стоит заметно дороже.

## 10. Доступность и отказоустойчивость

```
Последовательный участок:   A = Π A_i
Резервированная группа n из k:  A = Σ_{j=k..n} C(n,j) · A_i^j · (1−A_i)^(n−j)
Учёт failover:              A_eff = A − (failuresPerYear · (mttrSec + failoverSec)) / 31 536 000
Доступность Flow:           A_flow = Π по критическому пути
Error budget:               (1 − A_flow) · 43 200 мин/мес
```

**SPOF-детектор:** для каждого узла критического пути проверяется, есть ли альтернативный путь при
его удалении (по сути — поиск точек сочленения / мостов в графе Flow). Узел без резерва и с
`instances = 1` или с `azSpread = 1` — Finding `spof`. Блоки с флагом `managed` в определении
(`cdn`, `dns`, `glb`, `s3`, `dynamodb`, `sqs`, `serverless`) из проверки исключены: избыточность
внутри такого сервиса держит провайдер, а счётчика инстансов у него нет. Тот же флаг убирает их
из антипаттерна `over-provisioned` и из оси рубрики «Запас прочности» — за простой usage-priced
сервиса никто не платит.

**Домены отказа:** узлы внутри одной группы `az` падают вместе в сценарии `az-failure`.

## 14. Как мы проверяем, что модель не врёт

Эта секция — ответ на риск **R1** из PRD.

1. **Золотые схемы.** 12 эталонных схем с вручную посчитанными ожидаемыми метриками; снапшот-тесты
   в Vitest. Любое изменение формул ломает снапшот и требует осознанного обновления.
2. **Проверки размерности.** Автотест: все формулы согласованы по единицам (rps × байт = байт/с).
3. **Проверки предельных случаев.** ρ→0 ⇒ W_q→0; ρ→1 ⇒ W_q→∞; c→∞ ⇒ W_q→0; hit ratio при M≥N ⇒ 1.
4. **Сверка с теорией очередей.** Для M/M/1 численный результат сверяется с точной формулой
   `W_q = ρ·S/(1−ρ)` (расхождение аппроксимации < 5%).
5. **Сверка с публичными бенчмарками.** Дефолты по Postgres/Redis/Kafka сверяются с публичными
   замерами; в датасете хранится ссылка и дата.
6. **Явные допущения в UI.** У каждой сложной метрики — иконка ⓘ с формулой, подставленными
   числами и списком допущений. Пользователь всегда видит, что это оценка, а не измерение.
7. **Дисклеймер уровня продукта:** «Это обучающая модель. Она правильно передаёт *порядки величин* и
   *относительные эффекты* архитектурных решений, но не заменяет нагрузочное тестирование».

### 15.2. Расхождения с планом — принятые решения

**Flow — это клиентский блок.** Отдельной сущности Flow нет: каждый блок группы `clients`
задаёт один поток, `λ = dau · sessionsPerUserDay · requestsPerSession / 86400`, смесь операций —
из `readWriteMix`. Несколько именованных сценариев поведения на одном клиенте и покомпонентное
распределение `clientGeo` (§3.4) не реализованы; гео берётся из параметра региона и клиента целиком.

**Ветвление против веера.** Узлы групп `edge` и `clients` делят исходящий трафик между рёбрами
пропорционально `weight` (сумма долей = 1) — это балансировка. Все остальные узлы трактуют каждое
исходящее ребро как отдельный вызов на запрос (`fanout`). Это правило заменяет ручное задание
`share_e` из §3.1. **Свёртка задержек следует тому же правилу**: у балансирующего узла сэмпл идёт
ровно в одно плечо, выбранное по весам, а не суммирует все; у остальных узлов ребро повторяется
`fanout` раз. Пока обход суммировал все плечи, мульти-CDN и мультирегион завышали p99
пропорционально числу плеч, а `fanout` не стоил ничего, кроме ёмкости.

**Поглощение кэшем выводится из графа и касается только чтений.** Если узел вызывает и кэш, и
хранилище, у рёбер к хранилищам (`sql`, `nosql`, `search`, `olap`, `storage`) на `1 − h`
умножаются вызовы операций `read`, `scan`, `consume`, где `h` — hit ratio кэша-соседа; `write`,
`delete`, `publish`, `transfer` доходят до хранилища целиком. Отдельно узел с собственным параметром `cacheHitRatio` (CDN) или
`resolverCacheHitRatio` (DNS) поглощает эту долю всех своих исходящих вызовов. В Monte-Carlo то же
самое разыгрывается по Бернулли, поэтому промах виден как второй горб на распределении задержки.

**Отказ уводит трафик к живым, а не в никуда.** Балансирующие узлы (`edge`, `clients`) делят
исходящий трафик по весам только между целями, которые сценарий не выключил, и перенормируют
доли; если под отказ попал сам клиент, его λ раскладывается по выжившим клиентам пропорционально
их нагрузке. Иначе `region-failure` не нагружал бы выживший регион, а вдвое разгружал бы схему —
и отказ выглядел бы полезнее baseline. Выключенный узел при этом продолжает показывать пришедший
к нему поток при нулевой ёмкости: в transient-ряде это его доля ошибок, а не тишина.

**Полезная нагрузка живёт на ребре.** `avgRequestKb` / `avgResponseKb` клиента подставляются в
профили вызова в момент создания ребра (`applySourcePayload`), дальше по цепочке payload не
наследуется — его задаёт каждое ребро само. Иначе один параметр клиента описывал бы и видео-чанк,
и JSON-ответ API.

**`originLatencyMs` у CDN — это задержка ребра к origin**, а не слагаемое во времени обслуживания
CDN. Так нарисованный origin не считается дважды.

**A1 переформулирована под доступные параметры.** Вместо `E_Δt[P(L > Δt)]` считается вероятность
того, что в тот же ключ была запись за время, сравнимое со средним лагом:
`P = 1 − e^(−λ_write,key · E[L])`, где `λ_write,key = λ_write / effectiveKeys`, а `effectiveKeys`
берётся из `rowCount` / `uniqueKeys` / `documentCount` / `itemCount` блока.

**Transient-сценарии заданы амплитудами, а не абсолютами.** `slow-dependency` умножает время
обслуживания внешней зависимости на 25 вместо «p99 = 5 с» из §12: у зависимостей разная база, и
множитель переносится между схемами, а абсолютная цифра — нет. `growth` растит трафик ×10 за два
года, а обещанный ×10 объём данных получается сам — из выросшего потока записей в §8.
`black-friday` — плато ×20 на 4 часа с трапецией разгона по 15 минут и ×1.5 к payload. Множитель
времени обслуживания при этом делит ёмкость узла (`C_eff = C·scale_capacity / scale_service`), что
верно для ограничителей по числу приборов и завышает ёмкость там, где узел упирается в полосу.

**Worst-moment вместо среднего.** Стационарный срез transient-сценария считается в худшей точке
воздействия, а не в средней по горизонту: иначе `db-failover` со сорокасекундным окном на
пятиминутном горизонте выглядел бы как «почти baseline», и все предикаты заданий проходили бы.

**Константы, введённые движком** (их нет в параметрах блоков, они задокументированы здесь):

| Константа | Значение | Где | Смысл |
|---|---|---|---|
| `READ_AFTER_WRITE_SHARE` | 0.5 | `consistency.ts` | Доля записей, за которыми следует чтение тех же данных |
| `READ_AFTER_WRITE_GAP_SEC` | 1 с | `consistency.ts` | Типичная пауза между записью и чтением |

### 15.3. Не реализовано

* **`split-brain`** (§12) — единственный transient-сценарий, оставшийся нереализованным. Ему нужна
  не форма воздействия во времени, а модель расхождения и слияния реплик при разрыве связи:
  сейчас `consistency.ts` считает аномалии стационарно из лага репликации и не умеет ни копить
  дивергенцию за время разрыва, ни разрешать её после восстановления. Изображать разрыв
  выключением межрегиональных рёбер без этой механики значит показать пользователю цифру, за
  которой ничего не стоит.
* **`scaleUpLagSec` / `scaleDownLagSec` заведены только у `service`**: у остальных блоков лаг
  автоскейлера берётся из констант движка (§15.2), задать его на узле нельзя.
* **`lost-update` и `duplicate-processing`** (§12) остаются частью модели аномалий и отдельными
  сценариями не заведены.
* **Ряд `timeline` не участвует в приёмке заданий** (`docs/04-challenges.md`): предикаты
  по-прежнему смотрят на стационарный срез, который для transient-сценария берётся в худшей точке
  воздействия.
* **Гарантия порядка задаётся не везде** (A7, §7а.2): `orderingScope` есть только у Kafka,
  `queueType` — только у SQS. RabbitMQ, NATS, Kinesis, Redis Streams и SNS считаются
  неупорядоченными без возможности заявить обратное, даже если в реальной постановке порядок
  обеспечен ключом партиционирования на стороне продюсера.
* **A8 не различает три свои аномалии по частоте**: грязное, неповторяющееся и фантомное чтение
  выводятся с одной оценкой сверху и признаком `upperBound`. Разделить их — значит завести модель
  длительности транзакции и её фаз, которой нет: окно берётся как `serviceSec · 2`.
* **`deliverySemantics` на async-ребре** (`at-most-once` / `at-least-once` / `effectively-once`):
  поля в `EdgePolicy` нет, дубликаты A6 всегда считаются по семантике `at-least-once`, а гасит их
  только идемпотентность ребра или консьюмера.
* **Зеркальные регионы `mirrorOf`** (§3.4): регионы описываются явно, каждый своими узлами.
* **Инкрементальный пересчёт** по хэшу подграфа (§13): пересчитывается вся схема целиком.
  На демо-схемах это 40–60 мс, поэтому пока не мешает.
* **Автоскейлинг** реализован у `service` (по целевой утилизации) и у `ws-gateway` (по числу
  соединений) — у остальных блоков число инстансов задаётся руками.
* **Рост кластера ничем не ограничен сверху.** При `autoscaleNodes = true` `k8s-cluster`
  доращивает ноды под любое число подов: квоты облака, свободные адреса в подсети и наличие
  инстансов нужного типа не моделируются. Параметра-потолка нет ни в одном документе, поэтому он
  не заведён; если заводить — имя `maxNodes` уже занято ограничением схемы в заданиях
  (`challenge.constraints.maxNodes`), и брать его нельзя.
* **Медленная зависимость не удлиняет обслуживание вызывающего.** `serviceSec` — статический
  параметр блока, в него не входит ожидание downstream. Поэтому перегрузка внизу стека не
  поднимает ρ вверх по стеку: каскад (§5.3) доезжает наверх ошибками и ретраями, но не ёмкостью.
* **Веер в `parallel` ограничен `MAX_CALLS_PER_EDGE`** без поправки на порядковую статистику:
  при `fanout > 16` и `callMode = parallel` максимум берётся по 16 разыгранным вызовам, то есть
  хвост «tail at scale» занижен. В `sequential` остаток учтён масштабированием.
* **Падение write-throughput от синхронной репликации** (§7а.3): ожидание подтверждения попадает
  в latency записи, но не уменьшает ёмкость хранилища — для этого нужно, чтобы `serviceSec` блока
  зависел от `replicationMode`.

### 15.4. Как проверяется модель

Из семи пунктов §14 реализованы четыре, тестами в `tests/engine/`:

|---|---|---|
| Сверка с теорией очередей | `model-validation.test.ts` | `W_q` для M/M/1 совпадает с точной формулой `ρS/(1−ρ)`, расхождение < 5% |
