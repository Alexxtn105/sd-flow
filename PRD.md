## 1. TL;DR

SysDesign Flow — браузерный **node-based редактор архитектурных схем с работающим симулятором нагрузки**.
Пользователь собирает схему из «строительных блоков» (клиенты, балансировщики, гейтвеи, сервисы,
БД, кэши, брокеры, объектные хранилища, CDN), задаёт параметры каждого блока и профиль трафика —
а движок в реальном времени считает: сколько RPS схема выдержит, где узкое место, какая
latency p50/p95/p99, сколько терабайт данных и логов накопится за год, во сколько это обойдётся
в месяц и что сломается при отказе зоны доступности.

Два основных режима:

* **Песочница** — свободное конструирование + живая телеметрия + «что если» (всплеск ×3, падение Redis, отказ AZ).
* **Задания** — уровни от «сократитель ссылок» до «спроектируй YouTube»: ТЗ с исходными данными и
  нефункциональными требованиями, автоматическая **приёмка** решения (без единственно правильного ответа —
  через набор предикатов, прогон сценариев-стресс-тестов и балльную рубрику).

Стек и визуальные паттерны наследуются от `dsp-flow`: React 19 + `@xyflow/react`, палитра слева с
drag&drop, кастомные ноды и рёбра, реестр плагинов, инлайн-редактирование параметров, i18n (ru/en),
тёмная/светлая тема, localStorage, статический деплой на GitHub Pages.

## 2. Проблема и аудитория

### 2.1. Проблема

Подготовка к System Design интервью и обучение проектированию нагруженных систем сегодня —
это чтение книг (DDIA, Alex Xu), просмотр видео и рисование статичных картинок в Excalidraw/Miro.
Ключевые дефициты:

| Дефицит | Следствие |
|---|---|
| Схема ничего не «делает» | Нельзя проверить: выдержит ли твоя схема 50k RPS |
| Нет обратной связи | Ошибки в capacity estimation обнаруживаются только на интервью |
| Арифметика делается «в столбик» | 80% времени уходит на счёт, а не на архитектурные решения |
| Нет тренировки на отказах | Кандидат не готов к вопросу «а если упадёт AZ / кэш холодный / хот-ключ?» |
| Нет объективной оценки | Непонятно, «сдал» ты своё домашнее проектирование или нет |

### 2.2. Персоны

| Персона | Кто | Задача (JTBD) | Что для неё критично |
|---|---|---|---|
| **P1. Кандидат** | Middle/Senior backend, готовится к интервью в 2–8 недель | «Хочу за месяц набить руку на 20 типовых задачах» | Задания по уровням, приёмка, эталонные решения, таймер |
| **P2. Практик** | Тимлид/архитектор, планирует реальную мощность | «Прикинуть, хватит ли 6 подов и одной реплики Postgres» | Точность модели, экспорт, свои цены, кастомные блоки |
| **P3. Студент/джун** | Учится, слабо чувствует порядки величин | «Понять, почему тут нужен CDN, а тут очередь» | Подсказки, объяснения «почему упёрлось», туториал |
| **P4. Интервьюер/преподаватель** | Проводит собеседования, ведёт курс | «Дать задачу и объективно оценить» | Конструктор заданий, шаринг схем, отчёт по рубрике |

### 2.3. Anti-persona

Не целимся в: SRE, которому нужен точный capacity planning продакшена (нужен трейс-driven анализ),
и в enterprise-архитектора, которому нужен ArchiMate/C4-нотация и compliance-документация.

## 3. Цели, антицели, метрики успеха

### 3.1. Цели продукта

**G1.** Дать «физику» системному дизайну: любое архитектурное решение немедленно отражается в числах
(RPS, latency, $, ТБ, девятки).
**G2.** Сделать 20+ канонических задач System Design проходимыми в формате игры с уровнями и оценкой.
**G3.** Научить порядкам величин (back-of-the-envelope) через мгновенный пересчёт, а не через таблички.
**G4.** Дать «тренажёр отказов»: любая схема прогоняется через батарею сценариев деградации.
**G5.** Остаться полностью клиентским статическим приложением (GitHub Pages, оффлайн, без бэкенда) в MVP.

### 3.2. Антицели (осознанно НЕ делаем)

* **NG1.** Не делаем IaC-генератор: схема не превращается в Terraform/Helm (может быть в v2 как экспорт-стаб).
* **NG2.** Не претендуем на симулятор production-точности. Модель — обучающая, с явно опубликованными допущениями.
* **NG3.** Не делаем совместное редактирование в реальном времени в MVP (только шаринг ссылкой/файлом).
* **NG4.** Не делаем мониторинг реальных систем и импорт реальных метрик.
* **NG5.** Не делаем сетевой симулятор пакетного уровня (TCP/QUIC-механика вне модели).

### 3.3. Метрики успеха

| Метрика | Целевое значение (через 6 мес.) |
|---|---|
| TTFV (time to first value): от загрузки до первой посчитанной схемы | < 90 сек |
| Доля сессий, где запущена симуляция | > 70% |
| Доля новых пользователей, сдавших ≥ 1 задание | > 40% |
| Средняя глубина прохождения (заданий за пользователя) | ≥ 4 |
| Возврат на 7-й день (D7) | > 20% |
| Доля схем, которыми поделились (share-link/экспорт) | > 15% |
| Время симуляции схемы на 100 узлов | < 100 мс (steady-state), < 1.5 с (батарея сценариев) |

## 5. Доменная модель и ключевые концепции

Восемь сущностей. Всё остальное — производное.

```
Project
 └── Scheme (схема / решение)
      ├── Node[]      — блок (компонент архитектуры)
      ├── Edge[]      — связь (вызов между блоками)
      ├── Group[]     — контейнер: Region / AZ / VPC / K8s-cluster
      ├── Flow[]      — пользовательский сценарий, порождающий трафик
      ├── Probe[]     — измерители, прикреплённые к точкам схемы
      └── Scenario    — активный сценарий нагрузки/отказа
Challenge (задание) → Requirement[] + ScenarioBattery[] + Rubric
SimulationResult → NodeMetrics[], EdgeMetrics[], FlowMetrics[], Findings[]
```

### 5.1. Node (блок)

Экземпляр **типа компонента** из реестра. Аналог плагина в `dsp-flow`:

```ts
interface SchemeNode {
  id: string;
  type: ComponentTypeId;
  label: string;
  groupId?: string;
  position: XYPosition;
  params: Record<string, ParamValue>;
  scaling: { instances: number; autoscale?: AutoscalePolicy };
}
```

### 5.2. Edge (связь)

Направленный вызов. Несёт **профиль вызова**, а не просто «стрелочку»:

```ts
interface SchemeEdge {
  id: string; source: string; target: string;
  sourceHandle?: string; targetHandle?: string;
  kind: 'sync' | 'async' | 'replication' | 'stream' | 'cdc' | 'batch';
  protocol: 'http' | 'grpc' | 'sql' | 'redis' | 'kafka' | 'amqp' | 's3' | 'ws' | 'internal';
  ops: { readShare: number; writeShare: number };
  fanout: number;
  payload: { requestBytes: number; responseBytes: number };
  policy: { timeoutMs: number; retries: number; retryBudget: number; circuitBreaker: boolean; idempotent: boolean };
  weight?: number;
}
```

Подробный разбор семантики read/write и визуализации — **[docs/03-connections.md](docs/03-connections.md)**.

### 5.3. Flow (пользовательский сценарий) — источник трафика

Ключевая идея модели: **трафик порождают не блоки, а сценарии использования**.
«Просмотр видео», «загрузка видео», «поиск» — три разных Flow с разными RPS, payload и SLO.
Один блок обслуживает несколько Flow одновременно, а latency и SLO считаются отдельно по каждому.

```ts
interface Flow {
  id: string; name: string;
  entryNodeId: string;
  rps: { average: number; peakFactor: number; dailyPattern?: DiurnalCurve; growthPerYear?: number };
  mix: { readShare: number; writeShare: number };
  slo: { p99Ms?: number; p95Ms?: number; availability?: number; errorBudget?: number };
  clientGeo?: GeoDistribution;
  weightInScore: number;
}
```

### 5.4. Group (топологический контейнер)

Region / Availability Zone / VPC / Kubernetes cluster. Реализуется через parent-nodes React Flow.
Определяет **сетевую задержку между блоками** и **домен отказа** (что падает вместе).

### 5.5. Probe (измеритель)

Прямой аналог блоков `visualization` из `dsp-flow`: перетаскивается на схему, прикрепляется к узлу
или ребру и открывает окно с графиком. Типы: RPS-метр, Latency-гистограмма, Utilization-датчик,
Queue-depth, Storage-projection, Cost-метр, SLO-индикатор, Traffic-inspector.

### 5.6. Scenario (сценарий нагрузки/отказа)

Пресет, изменяющий условия прогона: `baseline`, `peak×3`, `growth×10`, `az-failure`,
`cache-flush`, `db-failover`, `hot-key`, `slow-dependency`, `thundering-herd`, `black-friday`.
См. **[docs/02-simulation.md](docs/02-simulation.md)** и **[docs/04-challenges.md](docs/04-challenges.md)**.

### 5.7. SimulationResult

Что возвращает движок: метрики по каждому узлу/ребру/потоку + список **Findings**
(bottleneck, SPOF, anti-pattern, SLO violation, budget overrun) с привязкой к узлу и объяснением.

### 5.8. Challenge (задание)

ТЗ + машиночитаемые требования + батарея сценариев + рубрика оценки.
См. **[docs/04-challenges.md](docs/04-challenges.md)**.

## 6. Режимы работы

### 6.1. Песочница (Sandbox) — MVP

Свободное конструирование без ограничений и без оценки.

* Палитра всех блоков, любой размер схемы.
* Панель **Traffic**: создаёшь Flow, крутишь ползунки DAU / RPS / peak factor / размер payload —
  метрики пересчитываются на лету (debounce ~150 мс).
* Дашборд «Итог по системе»: суммарный RPS, «потолок» системы (максимальный RPS до первой
  насыщенной точки), p99 по каждому Flow, $/мес, ТБ/год (данные + логи + метрики + бэкапы),
  доступность (девятки), список узких мест.
* Кнопка **«Найти потолок»** (`capacity sweep`): бинарный поиск по множителю трафика — «ваша схема
  держит 47 300 RPS, дальше упирается в Postgres (connections)».
* Кнопки сценариев отказов — одним кликом «убить» AZ или целый регион, сбросить кэш, замедлить внешний API.
* Панель **Согласованность**: частота аномалий по типам (устаревшие чтения, нарушения read-your-writes,
  потерянные обновления, конфликты мульти-мастера, дубликаты) — в операциях в секунду и в процентах,
  с указанием, какое ребро/хранилище их порождает. Отключается настройкой FR-PLT-7.
* Режим **X-ray**: подписи с числами на всех рёбрах и узлах.
* Сохранение/загрузка/экспорт/шаринг.

### 6.2. Выполнение заданий (Challenges) — MVP

* Каталог заданий, сгруппированных по уровням 1–5, с прогрессом и звёздами (1–3).
* Экран брифинга: легенда задачи, функциональные требования, нефункциональные (SLO, бюджет,
  горизонт роста), исходные данные (DAU, RPS, размеры), явные ограничения.
* Рабочая область — тот же канвас, но с **панелью требований справа**: каждое требование —
  чекбокс, который загорается зелёным по мере того, как схема начинает ему удовлетворять (живая обратная связь).
* Кнопка **«Сдать на приёмку»** → прогон батареи сценариев → отчёт с рубрикой и звёздами.
* Подсказки трёх уровней (наводящий вопрос → направление → прямая подсказка), каждая снимает баллы.
* После сдачи — **эталонные решения** (2–3 варианта) с разбором трейд-оффов и диффом с твоим решением.

### 6.3. Режимы дорожной карты (post-MVP)

| Режим | Суть |
|---|---|
| **Туториал** | 5 интерактивных шагов на живой схеме: добавь блок → соедини → запусти → почини → сдай |
| **Интервью (таймер)** | 45 минут, требования «подкидываются» этапами: сначала базовый сервис, на 20-й минуте «а теперь ×10 пользователей», на 35-й «а теперь мультирегион» |
| **Инцидент («почини схему»)** | Дана готовая, но падающая схема + симптом («p99 = 4 с при пике»). Найди и почини причину |
| **Гольф (оптимизация)** | Схема должна держать фиксированный SLO при минимальной стоимости. Лидерборд по $/мес |
| **Дуэль** | Асинхронное сравнение двух решений одной задачи по рубрике |

## 7. Пользовательские сценарии

### 7.1. Первый запуск (P3, джун)

Сделано в фазе 3 как интерактивный туториал из восьми шагов. Схему не подставляет никто: её
собирает пользователь, туториал подсвечивает нужный элемент интерфейса, объясняет его одной-двумя
фразами и сам замечает выполненное действие.

1. Открывает URL → пустой канвас и карточка по центру: «Соберём схему из двух блоков и посмотрим,
   какую нагрузку она держит и где узкое место». Приходит только при первом запуске.
2. Подсвечена палитра: перетащить «Веб-клиенты», следом «Сервис». Каждый шаг закрывается сам,
   как только блок оказался на канвасе.
3. Подсвечен канвас: соединить клиента с сервисом. Шаг закрывается по появлению связи.
4. Подсвечены итоги дашборда: схема пересчиталась сама, видны суммарный RPS, стоимость,
   доступность.
5. Подсвечен **ограничитель** под блоком — «процессор», «пул соединений», «память»: главный ответ
   симуляции на вопрос «где узко». Клик по блоку открывает параметры в инспекторе и переводит шаг.
6. Подсвечены Findings: симптом → причина → что попробовать; клик по находке подсвечивает блоки,
   о которых она говорит.
7. Финал: «Открыть задания» или «Готово».

Любой шаг пропускается кнопкой, весь туториал закрывается крестиком или Escape и сам больше не
приходит: отметка о прохождении лежит в `sd-preferences` рядом с размерами панелей, перезапуск —
кнопка в шапке. Схему пользователя туториал не трогает и ничего не затирает: шаги считают только
то, что добавлено после начала шага, поэтому туториал работает и на непустом канвасе.

### 7.2. Прохождение задания «YouTube» (P1, кандидат)

1. Каталог → уровень 4 → «Видеохостинг (YouTube-like)» → брифинг.
2. Читает исходные данные: 100M DAU, 5 просмотров/день, средняя длительность 6 мин, 1080p (4.5 Мбит/с),
   50k загрузок/день по 10 мин. SLO: старт воспроизведения p99 < 300 мс, доступность 99.95%,
   бюджет ≤ $X/мес, хранение 3 года.
3. Собирает схему за 20–40 минут. Панель требований показывает: 7 из 11 зелёные.
   Красным горит «egress ≤ бюджета» — потому что он раздаёт видео напрямую из S3.
4. Добавляет CDN → egress-стоимость падает в 6 раз, требование зеленеет.
5. «Сдать» → прогон 9 сценариев → 2 звезды: SLO выполнен, но при сценарии `hot-key`
   («ролик стал вирусным») деградировал метаданный Postgres.
6. Читает finding, добавляет кэш метаданных, пересдаёт → 3 звезды.
7. Смотрит эталонное решение, видит, что там ещё вынесли транскодинг в очередь с приоритетами.

### 7.3. Прикидка мощности (P2, практик)

1. Импортирует схему из JSON (или собирает).
2. Переключает Pricing profile на «свой» и вбивает реальные цены своего облака/железа.
3. Задаёт реальный профиль трафика из своих метрик.
4. Прогоняет `growth×10`, смотрит, что упрётся первым и через сколько месяцев.

### 9.2. Узел (Node)

```
┌────────────────────────────┐
│ ⬤ PostgreSQL      [primary]│  ← иконка + имя + бейдж роли
│ db.r6g.2xlarge × 1 + 2 RR  │  ← краткая конфигурация
│ ▓▓▓▓▓▓▓▓░░ 0.81            │  ← бар утилизации, цвет = состояние
│ 8.2k rps · p99 24 ms       │  ← живые метрики (скрываются на мелком зуме)
└────────────────────────────┘
   ◀ входные порты      выходные порты ▶
```

Состояния узла (цвет рамки/бара):

| Состояние | ρ | Цвет | Поведение |
|---|---|---|---|
| idle | 0 | серый | нет трафика — предупреждение «блок не используется» |
| ok | < 0.6 | зелёный | — |
| warm | 0.6–0.8 | жёлтый | — |
| hot | 0.8–1.0 | оранжевый | значок ⚠, растёт очередь |
| saturated | ≥ 1.0 | красный, пульсация | сброс запросов, каскад вверх по стеку |
| failed | — | серый в полоску | выключен сценарием отказа |
| misconfigured | — | красный контур пунктиром | ошибка валидации |

Level-of-detail: на зуме < 0.6 узел схлопывается в иконку + имя.

### 9.3. Ребро (Edge) — визуализация трафика

Прямое развитие идеи `RealSignalEdge` / `ComplexSignalEdge` из dsp-flow, где комплексный сигнал
рисуется двумя параллельными пунктирами со смещением.

| Визуальный признак | Что кодирует |
|---|---|
| Толщина линии | `1 + 1.6·log10(rps)` px, клампится 1–8 px |
| Число «жил» | 1 жила — только чтение или только запись; 2 жилы со смещением ±2.5 px — смешанный трафик (верхняя = read, нижняя = write) |
| Цвет жилы | read — голубой `--traffic-read`; write — янтарный `--traffic-write`; replication — фиолетовый; event/async — зелёный; blob/stream — широкая полупрозрачная лента |
| Штрих | sync — сплошная; async — пунктир; batch — длинный штрих-точка |
| Анимация | бегущий пунктир, скорость ∝ throughput (МБ/с), пауза при остановленной симуляции |
| Насыщенность/красный отлив | утилизация приёмника ρ; при ρ≥1 линия краснеет и появляются «отскакивающие» частицы (дропы) |
| Значок на середине | ⏱ таймаут, ↻ ретраи, ⚡ circuit breaker открыт, 🔒 идемпотентность |
| Подпись (X-ray) | `12.4k rps ↑ · 3.1k rps ↓ · 4.2 MB/s · p99 8 ms` |

**Решение по вопросу «read/write — одна линия или две»:** по умолчанию **одно логическое ребро с
двумя визуальными жилами**; действие «Разделить на read/write» создаёт два независимых ребра, когда
чтение и запись идут к разным целям (реплика vs primary, CQRS). Полное обоснование и альтернативы —
**[docs/03-connections.md](docs/03-connections.md)**.

### 9.4. Обратная связь и обучение

* **«Почему?»-объяснения**: у любого числа в доке есть раскрытие с формулой и подставленными значениями.
  `capacity = min(instances×workers/S = 8×64/0.012 = 42.7k, connections/1 = 500 …) → 500 rps (bound: connections)`
* **Findings** формулируются как «симптом → причина → что попробовать», без прямого ответа в режиме заданий.
* **Порядки величин**: числа всегда с единицами и человекочитаемым форматом (`101 PB/day`, `9.4 Tbps`).
* Наведение на узел подсвечивает все Flow, которые через него проходят.

### 11.1. Модули ядра (прямые аналоги dsp-flow)

| dsp-flow | SysDesign Flow | Роль |
|---|---|---|
| `PluginRegistry` | **`ComponentRegistry`** | Реестр типов блоков; регистрация групп; freeze после инициализации |
| `plugins/*` | **`components/*`** | Один тип компонента = один модуль: метаданные + схема параметров + `capacity` + `derive` |
| `GraphCompiler` | **`TopologyCompiler`** | Валидация связей, поиск компонент связности, SCC вместо запрета циклов, порядок обхода |
| `DSPProcessor` | **`SimulationEngine`** | Решатель потоков + очередей + Monte-Carlo latency + сценарии |
| `ValidationService` | **`RuleEngine`** | Антипаттерны, best-practice-линтер, hard gates заданий |
| `visualization/*` | **`probes/*` + `dashboards/*`** | Метры, графики, окна |
| `useDSPSimulation` | **`useSimulation`** | Жизненный цикл расчёта, debounce, отмена, прогресс |
| `pluginHelp.js` | **`componentHelp`** | Справка по блоку: назначение, параметры, когда применять, типовые ошибки |

**Ключевое отличие движка от dsp-flow:** в DSP граф ациклический и обходится топологической сортировкой
один раз. В system design циклы легальны и осмысленны (ретраи, cache-aside, двусторонняя репликация,
feedback от автоскейлера), поэтому решатель — **итеративный с фиксированной точкой** (Гаусс–Зейдель,
демпфирование, ≤ 50 итераций, критерий сходимости по δ‖λ‖ < 0.1%).

Подробности — **[docs/05-architecture.md](docs/05-architecture.md)**.

## 12. Дорожная карта и объём MVP

### Фаза 0 — Скелет ✅ сделано

Каркас приложения из dsp-flow: канвас, палитра, инспектор, темы, i18n, хранение, CI.
Цель — работающий редактор схем — достигнута.

Фактический объём оказался шире плана: вместо 15 блоков-заглушек описан **весь каталог первой
волны — 44 блока** (декларативная часть: порты, `defaultParams`, `paramSchema`), потому что
определение блока без модели стоит ~25 строк, а неполная палитра мешает проверять раскладку UI.
Также сразу подняты группы-контейнеры Region/AZ (ADR-11) и рёбра с профилями вызова (ADR-6).
Модель нагрузки (`capacity`/`cost`/`derive`) — необязательный слот `model` в контракте блока,
заполняется в фазе 1.

### Фаза 1 — MVP «Песочница» ✅ сделано

* `ComponentRegistry` + **44 блока** первой волны — модель заполнена у всех блоков, несущих трафик.
* Steady-state решатель: потоки с усилением ретраями, ёмкость с именованным ограничителем, утилизация, очереди, latency (Monte-Carlo), хранилище, стоимость, доступность.
* **Мультирегион:** группы Region/AZ, гео-маршрутизация, межрегиональные лаг и стоимость, режимы active-active / active-passive, RPO/RTO против целевых.
* **Модель согласованности с симуляцией аномалий** (режим по умолчанию): устаревшие чтения, read-your-writes, потерянные обновления, конфликты мульти-мастера, дубликаты обработки.
* Дашборд, Findings с переходом на узел, X-ray, метрики и полосы утилизации на узлах.
* Сценарии: baseline, peak, az-failure, **region-failure**, cache-flush, **stale-read**, **write-conflict**.
* **Definition of Done достигнут:** «Видеоплатформа» считается за 40–60 мс и даёт 106 ПБ/сут egress и 9.9 Тбит/с (101 ПБ/сут раздаёт клиентам CDN плюс 5 ПБ/сут наполнения кэша из origin — с честной атрибуцией egress оно тоже оплачивается, `docs/02-simulation.md` §9); «Платежи в двух регионах» показывают 0.2–0.8 оп/с конфликтов записи и вдвое меньшую скорость молчаливой потери записей при LWW, и обнуляют конфликты после переключения на single-writer-на-ключ. Оба факта закреплены тестами `tests/engine/demo-schemes.test.ts`.

**Не вошло в фазу и перенесено:** зеркальные регионы `mirrorOf`, тепловая карта и capacity sweep,
transient-сценарии, аномалии A3/A7/A8, окна проб. Полный перечень с причинами —

## 13. Риски и открытые вопросы

### 13.1. Риски

| # | Риск | Влияние | Митигация |
|---|---|---|---|
| R1 | **Модель врёт** и формирует ложную интуицию | Высокое | Публикуем формулы и допущения прямо в UI; константы с источниками и датой; маркировка «оценка ±X»; экспертный override; калибровка на публичных бенчмарках |
| R2 | **Приёмка отвергает валидные креативные решения** (false negative) | Высокое | Предикаты формулируются над *способностями и метриками*, а не над структурой; приёмка через сценарии, а не сравнение с эталоном; отчёт всегда показывает конкретное нарушенное требование; «апелляция» — кнопка «почему не зачли» с трассировкой |
| R3 | **Приёмка пропускает плохие решения** (false positive) | Среднее | Батарея сценариев + анти-паттерн-линтер + штраф за переусложнение и переплату |
| R4 | Взрыв объёма: 100+ блоков × 15 параметров | Высокое | Универсальное «ядро ёмкости» (единая формула для всех блоков); блоки — данные, а не код; поэтапный выкат по волнам |
| R5 | Производительность браузера на больших схемах | Среднее | Worker, мемоизация, инкрементальный пересчёт затронутого подграфа, LOD-рендер |
| R6 | Юридическое: названия и логотипы вендоров | Низкое | Только номинативное использование имён, свои иконки, дисклеймер |
| R7 | Продукт «для узкой аудитории» — низкий retention | Среднее | Контент-двигатель: регулярные новые задания, дуэли, шаринг решений в соцсети |
| R8 | Сложность онбординга (много параметров) | Среднее | Разумные дефолты + «Авто» у всех производных параметров + прогрессивное раскрытие (Basic/Advanced tabs) |

### 13.2. Решённые вопросы

| # | Вопрос | Решение (2026-08-14) | Последствия |
|---|---|---|---|
| D1 | Мультирегион в MVP или в фазе 3? | **В MVP.** Группы Region/AZ, гео-маршрутизация, межрегиональная репликация и RPO/RTO входят в фазу 1 | Блоки `region`, `link-cross-region`, `multi-region-policy`, `dns`, `glb` переведены в первую волну (44 блока вместо 39). Добавлены FR-CNV-6a/6b (зеркальные регионы, режимы отображения) и FR-SIM-15/16. Сценарий `region-failure` — обязательный в MVP. Одно задание уровня 5 переезжает в фазу 2 как приёмочный тест подсистемы |
| D2 | Насколько глубоко моделировать consistency? | **Вынесено в настройку** `выкл / атрибут / симуляция аномалий`, **по умолчанию — симуляция аномалий** | Новый солвер `ConsistencyModel`, FR-SIM-17/18, FR-PLT-7. Появляются метрики частоты аномалий, сценарии `stale-read`, `write-conflict`, `lost-update`, `duplicate-processing`, предикаты заданий по аномалиям и параметры-средства смягчения на блоках и рёбрах |
| D3 | Задания в YAML или в коде? | **В TypeScript-модулях** с типом `Challenge`; форма DSL из `docs/04-challenges.md` §2 сохранена | Опечатка в задании падает на компиляции, в бандл не тянется YAML-парсер. Авторский YAML-режим переезжает в FR-CHL-9 (фаза 3) |
| D4 | Как задание задаёт поток нагрузки? | **Стартовая схема с блоками-клиентами**, id узла равен id потока, параметры заперты `lockedParams` | Следствие решения фазы 1 «каждый клиент — один поток». Правка данных задания роняет Realism Gate с объясняющим вердиктом |
| D5 | Считать ли managed-сервисы точкой отказа? | **Нет**: у блоков `cdn, dns, glb, s3, dynamodb, sqs, serverless` появился флаг `managed` | Провайдер держит избыточность сам: такие блоки не попадают в SPOF, не штрафуются за низкую утилизацию и не участвуют в оси «Запас прочности» |

Эти два решения усиливают друг друга: межрегиональный лаг репликации — главный физический источник
аномалий согласованности, поэтому модель мультирегиона напрямую питает модель аномалий.

### 13.3. Открытые вопросы

1. **Гранулярность инстансов**: моделируем «пул из N инстансов» или каждый инстанс отдельно?
   *Предложение:* пул, а отдельные инстансы — только для сценариев отказа (убить 1 из N).
2. **Единица «пользователи»**: DAU + просмотров/день или сразу RPS? *Предложение:* оба, с
   двусторонним пересчётом (изменил DAU — пересчитался RPS, и наоборот).
3. **Нужен ли LLM-ревьюер** и как сохранить «статичность» приложения? *Предложение:* опциональный,
   с BYO-ключом пользователя, без него всё работает.
4. **Формат заданий**: YAML для авторства vs JSON для рантайма — компилировать на этапе сборки?
5. **Ценовые профили** быстро устаревают — как обновлять? *Предложение:* отдельный датасет с датой
   актуальности и предупреждением, PR-friendly.
6. **Насколько агрессивно зеркалить регионы?** Полное зеркало проще в UI, но реальные архитектуры
   часто асимметричны (главный регион + облегчённые). *Предложение:* зеркало по умолчанию с
   возможностью «отвязать» регион и пометкой асимметрии в рубрике.
